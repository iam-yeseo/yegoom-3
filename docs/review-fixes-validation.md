### 작업 1 (P1) 주식 주문 재시도 시 중복 체결 방지

**문제.** 주문마다 새 `requestId`를 만들어, 체결은 됐지만 응답만 잃은 주문을 사용자가 다시 누르면 새 주문으로 또 체결됐다.

**해결.**
- `src/stock-orders.ts`: 주문 ID와 전체 입력(종목·매수/매도·수량·가격 버전·계정)을 **보내기 전에** 계정별로 저장한다(`localStorage` `yegoom3:stock:order:<계정>`). 응답을 받지 못하면 같은 ID·입력으로만 다시 확인하고, 그 주문의 영수증이나 확정 거절을 받을 때까지 새 주문을 보내지 않는다.
- `src/screens/Stock.tsx`: 종목·목록 화면에 "주문 결과를 확인하고 있어요 / 아직 확인하지 못했어요" 상태와 **주문 결과 다시 확인** 버튼. 들어오자마자 한 번, 이후 5초·15초·45초 뒤와 온라인·탭 복귀 때 자동으로 다시 확인한다. 결과가 미확정이면 매매 버튼이 `이전 주문 결과를 먼저 확인해 주세요`로 잠긴다.
- 오류 구분: 서버가 **미체결을 확정한** 코드(`shared/stock-types.ts`의 `STOCK_ORDER_UNFILLED_CODES`: 장 마감·가격 변경·잔액/보유 부족·입력 오류 등)만 주문을 끝낸다. 그 밖의 4xx(401, 403, `ACCOUNT_CHANGED`, 모르는 코드), 5xx, 연결 오류는 "결과 확인 필요"로 남는다. 오프라인이라 아예 보내지 못한 첫 주문은 바로 끝낸다.
- `worker/stocks.ts`: 거절을 돌려주기 전에 같은 ID의 체결을 한 번 더 찾아 있으면 영수증으로 답한다(재시도와 원 요청이 겹칠 때의 `REQUEST_IN_PROGRESS` 거절 제거). `expectedUserId`가 세션과 다르면 `409 ACCOUNT_CHANGED`로 거절해, 저장된 주문이 같은 브라우저의 다른 계정으로 체결되지 않는다. 소유권 검증, 같은 ID의 다른 입력 거절(`REQUEST_CONFLICT`), 원자적 거래·차감 batch는 그대로다.

### 작업 2 (P2) 마감 후에도 완료된 구매 결과 재조회 허용

**문제.** 23:49:59에 저장된 구매를 23:50 이후 같은 ID로 다시 확인하면 영수증 조회보다 마감 검사가 먼저 실행돼 `409 PLAY_CLOSED`가 났고, 클라이언트는 보류 요청을 지웠다.

**해결.**
- `worker/shop.ts`: 마감 검사(`requireOpenPlay`)를 각 구매 함수의 **영수증 조회 뒤**로 옮겨 신규 구매에만 적용한다(쿠지·로또·스피또·슬롯). 저장된 요청은 추가 차감·추첨·지급 없이 원래 결과를 돌려준다. 순서는 인증·역할 → 요청 형식 검증 → 영수증 조회 → 마감 → 신규 처리다.
- `src/api.ts` `refusedByServer`: 서버가 평가하고 거절한 응답에서만 보류 요청을 해제한다. 401·408·429, 5xx, 연결 오류는 유지한다. Provider(`src/shop.tsx`)와 슬롯·쿠지·태그 진화 화면이 같은 조건을 쓰므로 슬롯 화면의 재시도 ID가 Provider와 어긋나지 않는다.
- `src/screens/Shop.tsx`: 자정을 넘겨 확인한 스피또는 오늘 목록에 없으므로 저장된 결과를 모달로 바로 보여 준다.

**영향 파일.** `worker/shop.ts`, `src/shop.tsx`, `src/api.ts`, `src/screens/Slot.tsx`, `src/screens/Kuji.tsx`, `src/screens/Shop.tsx`, `src/screens/NicknameTagShop.tsx`

### 작업 3 (P2) 태그 조회와 변경이 겹칠 때 로딩 상태 복구

**문제.** 착용·버리기·진화가 진행 중인 조회를 무효화하면서 로딩을 해제할 주체가 없어져 `loading=true`가 남고 뽑기 버튼이 잠겼다.

**해결.** `src/shop-requests.ts`의 요청 게이트 하나로 조회·구매·태그 변경을 관리한다.
- 유효한 조회는 하나(최신)이고, 쓰기는 진행 중인 조회를 밀어낸다. 밀려난 응답은 상태를 덮어쓰지 않는다.
- `loading`은 유효한 조회나 쓰기가 진행 중일 때 켜지고, 마지막 것이 끝날 때 꺼진다. 다른 유효한 요청이 진행 중이면 먼저 꺼지지 않는다.
- 밀려나거나 쓰기 중에 요청된 조회는 쓰기 뒤에 다시 실행한다. 단, 쓰기 응답이 그 내용을 이미 담고 있으면 생략한다(실패한 쓰기 뒤에는 항상 다시 읽는다).

**영향 파일.** `src/shop-requests.ts`(신규), `src/shop.tsx`

**검증.**
- `tests/shop-requests.test.ts` 4개: 응답 순서 양방향, 실패 경로, 다른 종류의 밀려난 조회, 최신 조회 우선.
- `tests/e2e/tag-loading.spec.ts` 3개(실제 화면, 응답을 붙잡아 순서를 뒤집음): 착용(쓰기 먼저/조회 먼저), 버리기와 실패한 변경, 진화. 모두 최종 상태가 맞고 뽑기 버튼을 다시 쓸 수 있다.

## 묶음 2 — 캐치마인드·주식 상태 갱신

### 작업 4 (P2) 캐치마인드 그림의 해상도·픽셀 수 제한

**문제.** 약 279KB의 유효한 16,000×16,000 PNG가 검증을 통과했다(디코딩 크기 상한 없음).

**해결.** `shared/balance.ts`에 공통 규칙을 둔다: `maxImageSide` 1,024px, `maxImagePixels` 1,024×1,024(RGBA 4MiB). 캔버스는 680px이고 680·544·408·340px로 내보내므로 여유가 있다. `worker/catchmind.ts`의 `validateDrawing`이 PNG·WebP 모두 크기를 읽어 `shared/catchmind.ts`의 `catchmindImageSizeProblem`으로 검사하고, 넘으면 `413 IMAGE_DIMENSIONS_TOO_LARGE`("그림이 너무 커요. 가로세로 1,024픽셀 이하로…")를 돌려준다. 초안은 그대로 남아 다시 올릴 수 있다. 기존 압축 용량(300KiB)·형식·정사각형 검증은 그대로다.

**이미 저장된 이미지.** 다시 검사하지 않고 그대로 제공한다. 삭제·변환하지 않는다. 상한은 새 업로드에만 적용된다.

**영향 파일.** `shared/balance.ts`, `shared/catchmind.ts`, `worker/catchmind.ts`, `src/components/DrawingCanvas.tsx`

**검증.** `tests/integration.test.ts`: 약 30KB의 16,000×16,000 PNG, 1,025px PNG·WebP(손실·무손실·알파), 2,048×512, 1,024×1,025 거절 / 1,024px PNG·WebP 3종과 680px 캔버스 크기 통과 / 손상된 대형 파일은 `INVALID_IMAGE` / 거절 뒤 같은 초안에 다시 올리기 / 상한 이전에 저장된 1,025px 그림은 그대로 제공. 실제 캔버스 출력은 기존 캐치마인드 E2E가 그대로 통과한다.

### 작업 5 (P2) 캐치마인드 마감·재개 시 입력 권한 갱신

**문제.** 23:55에 받은 `canPublish=false`가 자정 뒤에도 남았다. 판 버전이 같아 폴링은 `unchanged`였고, 전체 응답도 같은 버전이라 무시됐으며, 초안 작성자는 폴링하지 않는다.

**해결.** 판 데이터와 시간에 따른 입력 가능 상태를 분리했다.
- 서버: `canPublish`·`canGuess`는 판과 역할만으로 정한다(시간 무관). 23:50~자정 마감은 모든 응답(`unchanged` 포함)에 `play: { closed, changesAt }`로 따로 내려 준다. `publish`·`guess`의 `PLAY_CLOSED` 검증은 그대로 서버가 한다.
- 클라이언트(`src/catchmind.tsx`): 응답의 `serverTime`으로 맞춘 서버 시계로 `changesAt`에 입력을 닫고 연다. 탭이 숨겨졌다 돌아오면 시계를 다시 읽는다. 창이 바뀌면 화면이 서버에 한 번 확인한다(폴링하지 않는 출제자 포함). Provider를 다시 만들지 않으므로 작성 중인 정답·그림·답변이 남는다.
- 호환: 예전 탭은 마감 중에도 입력이 켜져 보일 수 있으나 서버가 `PLAY_CLOSED`로 거절한다. `play`가 없는 응답은 `serverTime`으로 계산한다.

**영향 파일.** `shared/balance.ts`(`playWindow`), `shared/types.ts`, `worker/catchmind.ts`, `src/catchmind.tsx`, `src/screens/Catchmind.tsx`, `src/catchmind-preview.ts`

### 작업 6 (P2) 주식 뉴스 변경이 조건부 조회에 반영되도록 수정

**문제.** 시세 버전만 같으면 뉴스·잔액·보유량까지 포함한 응답 전체를 생략했다. 마감 시세를 먼저 조회한 뒤 저장된 마감 기사를 받지 못했다.

**해결.**
- `worker/stocks.ts` `readStockMarket`: 버전을 `시세 버전.표시 내용 지문`으로 만든다. 지문은 실제로 보여 줄 뉴스 5개, 마감 기사(시황·한 줄·주간), 골드, 보유량의 해시다. 시세가 같아도 이 중 하나가 바뀌면 전체 응답을 준다. 예전 형식(`시세 버전`만)의 `since`는 일치하지 않으므로 전체 응답을 받고, 이후로는 새 버전을 그대로 되돌려 보내면 된다(기존 클라이언트 코드 변경 불필요).
- 마감 기사 조회는 "최신 3개" 대신 최신 발행 시각만 읽는다. 보이는 마감 기사가 3개 미만이면 과거 뉴스를 계속 거슬러 읽던 문제가 있었다.
- `src/screens/Stock.tsx`: 장 마감 직후 마감 기사가 아직 없으면 30초마다(최대 15분) 다시 읽는다. 마감 뒤에는 다음 개장까지 틱이 없어, 다시 들어오기 전에는 읽을 계기가 없었다.
- `worker/index.ts`: 도전과제 판정은 시세가 실제로 움직인 조회에서만 실행한다.

**DB 비용.** 변경이 없을 때도 표시 행을 읽어야 변경 여부를 알 수 있으므로, 변경 없는 조건부 조회의 문장·행 수가 늘었다(아래 측정표: 4문장·19행 → 8문장·46행). 읽는 행은 표시 행뿐이라 뉴스 이력이 늘어도 같다. 조회는 화면이 보일 때 틱마다 한 번(장중 시간당 8번)이다. 전체 조회는 마감 기사 쿼리 수정으로 54행 → 46행이 됐다.

**영향 파일.** `worker/stocks.ts`, `worker/index.ts`, `src/screens/Stock.tsx`

### 작업 7 도전과제 판정을 활동별로 분리

**문제.** 모든 플레이어 쓰기 뒤에 한 문장으로 모든 사실을 다시 읽었고, 그 안에 주식 거래 전체 이력 계산이 들어 있었다.

**해결.** (`worker/achievements.ts`)
- 사실을 14개 활동 범위(`profile`, `attendance`, `tag`, `stock-trade`, `stock-market` …)로 나눈다. 쓰기 경로마다 그 활동만 판정한다(`achievementScopesFor`). 목록에 없는 경로는 전체 판정이라 새 엔드포인트가 조용히 빠지지 않는다.
- 판정은 ① 플레이어와 **이 판정이 추가할 수 있는 행만** 기본 키로 조회 → ② 아직 결정되지 않은 사실만 한 문장으로 조회 → ③ 새 달성이 있을 때만 쓰기 batch. 이미 달성한 일회성 과제의 사실은 읽지 않고, 범위의 일회성 과제를 모두 달성했으면 ②가 없다.
- 거래 사실(첫 매수·매도, 최고 수익·최대 손실, 상장폐지)은 거래 이력을 훑지 않는다. 마이그레이션 0031의 부분 인덱스 두 개로 매도 손익의 최대·최소와 상장폐지 행을 바로 읽는다. 인덱스는 SQLite가 거래와 같은 트랜잭션에서 갱신하므로 별도 요약값·초기 보정이 필요 없다.
- 상·하한가(과거 일봉 × 그날 보유 여부)는 플레이어별 확인 완료일(`achievement_scans.stock_limit_date`) 이후의 일봉만 읽는다.
  - 초기 보정: 행이 없으면 첫 판정이 첫 거래일부터 전부 읽는다(지금까지 매번 하던 일을 한 번).
  - 실패 복구: 확인 완료일은 달성 행·알림과 **같은 batch**로만 올라간다. 쓰기가 실패하면 그대로 남아 다음 판정이 같은 날을 다시 본다.
  - 재검증: `DELETE FROM achievement_scans [WHERE user_id = ?]` 뒤의 판정은 원본(`stock_daily`, `stock_trades`)에서 처음부터 다시 계산한다. 달성 행은 `INSERT OR IGNORE`라 중복되지 않는다.
- 놓치지 않기: 예측 정산(`settlePublishedRounds`)·로또 정산(`settleDueLotto`)·랭킹 Cron은 해당 범위로 판정한다. 시장 과제(상·하한가, 상장폐지)는 거래 뒤, 시세가 움직인 시장 조회, 그리고 **18:00 Cron의 보유자 일괄 판정**(`syncMarketAchievements`, 신규)으로 잡는다. 다른 사람의 10번째 오답으로 판이 끝날 때 출제자도 판정한다. 도전과제 화면은 전체 판정(안전망)이다.
- 달성 행 `(user_id, key, period_key)`와 알림 reference의 UNIQUE, 보상 원장 reference `achievement:<키>:<기간>:<계정>`, `claimed_at`과 원장을 한 batch로 쓰는 지급은 바꾸지 않았다.

- 도전과제 결과가 의심되면 `DELETE FROM achievement_scans`(전체 또는 해당 계정) 뒤 도전과제 화면을 열어 원본 이력으로 다시 판정한다.

  - 수정: `releaseClock(page)`(`page.unrouteAll({ behavior: 'ignoreErrors' })`)를 `ServerClock`을 쓰는 스펙 3개의 `afterEach`에서 호출해, 종료 시 진행 중이던 요청을 버린다. 함께, 준비 단계(`beforeAll`)가 중간에 끊기면 분리 실행한 서버가 남아 다음 실행의 포트에서 다른 DB로 응답하던 문제를 막았다(워커 종료 시 서버도 종료, 시작 전에 포트가 이미 응답하면 즉시 실패).
  - 검증: 세 스펙을 CI와 같은 설정으로 3회 반복해 15/15 통과(그동안에도 `SQLITE_BUSY` 재시도는 발생), 전체 E2E 150개 중 149개 통과(실패는 아래 기존 실패 1개), 실행 뒤 남은 서버 프로세스 없음.

## 남은 항목과 한계

- **운영 미적용.** 원격 마이그레이션·머지·배포는 하지 않았다. 운영 부하 검사도 하지 않았다.
- **작업 1의 이론적 경합.** 서버가 재시도를 확정 거절한 뒤에, 아직 도착하지 않았던 원 요청이 늦게 도착해 체결되는 경우는 막지 않았다. 이 경우가 되려면 원 요청이 재시도보다 늦게 처리되면서 그 사이 거절 사유(잔액·보유량 등)가 풀려야 한다. 가격 버전·장 시간 조건은 한 번 지나면 되돌아오지 않아 해당하지 않는다. 완전히 막으려면 거절한 주문 ID를 기록하는 표가 필요하며 별도 작업으로 남긴다. 상점·캐치마인드·뽑기의 기존 재시도도 같은 가정을 쓴다.
- **미리보기 주식 E2E 1건.** `stock-pr10.spec.ts:17`(미리보기 예굼 `20주 보유`)은 기준 커밋에서도 실패한다. 이번 변경과 무관해 고치지 않았다.
- **자기 범위 안의 이력 비례.** `kuji_a`, `tag_s`, `slot_jackpot`, 출석 합계 같은 사실은 달성 전까지 그 활동의 자기 이력을 읽는다. 다른 활동에는 영향이 없고 달성하면 읽지 않는다. 이번 범위(주식 이력)는 아니어서 두었다.
- **상·하한가의 일봉 조회.** 확인 완료일 이후의 일봉만 읽지만, 두 과제를 모두 달성하기 전에는 새 거래일마다 거래한 종목 수만큼 읽는다.
- **E2E 하네스.** 시간 경계 테스트는 한 D1을 여러 Worker 프로세스가 공유한다. 로컬 D1에는 busy timeout이 없어 간헐적으로 `SQLITE_BUSY`(500)가 나며, 하네스가 재시도한다(운영에는 없는 상황). `ServerClock`을 쓰는 새 스펙은 `afterEach`에서 `releaseClock(page)`를 불러야 한다(빠뜨리면 위의 종료 시점 실패가 간헐적으로 난다).
