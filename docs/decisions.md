# 구현의 범위와 결정

## 주간·월간 랭킹 보상 (2026-11-05)

- **요청:** 주간·월간 모두 `그 기간 점수 × 순위 배수`로 골드를 준다. 주간 배수는 1위 5·2위 4·3위 3. 최소 보장은 둔다. 동점은 공동 순위 그대로. 4위 이하는 나중에 정한다.
- **배수와 최소 보장(`shared/ranking-rewards.ts` 한 곳):** 주간 ×5·×4·×3에 최소 300·200·100G, 월간 ×2·×1.5·×1에 최소 600·400·200G. 월간 점수는 그 달 주간 점수의 합이라 같은 배수를 쓰면 랭킹 보상이 정확히 두 배가 되고 전체 골드 수입의 절반을 넘기므로 월간만 낮췄다(1위 기준 주간 2,060G/주, 월간 3,540G/월 수준). 소수 배수는 반올림한다.
- **최소 보장:** 활성 플레이어 전원이 받는다. 그래서 아무도 점수를 얻지 않은 주도 전원이 그 순위의 최소액을 받는다(전원 0점이면 모두 공동 1위라 1위 최소액). 기존 기획의 "3명 모두 일정 골드를 받되 차등"과 같은 뜻이다.
- **4위 이하:** 배수표에 없는 순위는 0원이다. 사람이 늘면 그때 표에 줄을 더한다.
- **정산:** 10분마다 도는 기존 Cron의 KST 00:00~00:10 구간에서 `settleDueRankingRewards`가 끝난 주(월요일)와 끝난 달(1일)을 지급한다. 지난 8주·3개월까지 거슬러 확인하므로 한 번 걸러도 다음 날 따라잡는다. `RANKING_REWARDS.*.from`(주간 2026-11-02, 월간 2026-11) 이전 기간은 절대 지급하지 않아 배포 즉시 과거가 소급되지 않는다.
- **멱등:** 지급 행 `rank:<week|month>:<키>:<userId>`와 `ranking_settlements(period, key)` 표(마이그레이션 0019)를 한 배치에 `INSERT OR IGNORE`로 넣는다. 재시도·동시 Cron·따라잡기가 겹쳐도 한 번만 지급한다. bootstrap에는 질의를 더하지 않았다(기존 쿼리 예산 유지).
- **순서:** 점수 내림차순·로그인 아이디 순으로 화면과 같은 공동 순위(1·1·3)를 매긴다. 운영자와 비활성 계정은 빠진다.
- **화면:** 랭킹 하단 `점수와 보상 규칙` 카드가 배수·최소액·지급 시각을 `shared` 값에서 만들어 적고, 주간·월간 탭에서는 "지금 순위 그대로면 N골드를 받아요"를 함께 보여 준다(일간은 보상이 없어 숨김). 지급은 내 정보의 골드 내역에 `주간/월간 랭킹 보상`으로 남는다. 당첨 배너는 `announcements.kind` CHECK를 바꿔야 해서 이번에는 넣지 않았다.

## 랭킹 보상 안내·시상대 별명·별명 뽑기권 (2026-11-05)

- **요청:** 주간 랭킹 보상을 어떻게 정했는지 랭킹 페이지 하단에 적고, 시상대에도 별명 태그를 `사진 / 별명 · 닉네임 / 점수` 3단으로 보여 주고, 모든 플레이어에게 별명 뽑기권 5장을 지급한다.
- **보상 상태(2026-11-05 당시):** 주간 순위 보상은 **지급하지 않음**이 유효한 결정이었다. 같은 날 위 "주간·월간 랭킹 보상"으로 다시 정해졌고, 카드 문구도 그 공식으로 바뀌었다. 당시 근거는 다음과 같다(`docs/plan-v2.md` §0-1·보류 사항, 이 문서 Phase 1). 순위별 액수는 정해진 적이 없고 예전 화면의 3,000/1,800/1,000G 표시는 Phase 1에서 뺐다. 그래서 하단 카드에는 금액 대신 지금 규칙(월~일 집계, 다음 주 0점 시작, 공동 순위, 보상 미지급, 정해지면 이 자리에 적음)만 적는다. 숫자를 문구에 하드코딩하지 않는다(§0-2).
- **시상대:** `사진 / [태그] 닉네임 / 점수` 3단으로 바꾸고 태그 칩을 숨기던 `.podium-name .nick-tag { display: none }`를 지웠다. 칸이 좁으면 태그가 윗줄로 접혀 닉네임은 잘리지 않는다. 블록 높이는 124·150·186 → 146·172·208로 키워 한 줄이 늘어난 만큼을 받았다.
- **뽑기권 저장:** 추가 전용 마이그레이션 `0018_tag_tickets.sql`. `inventory_ledger`의 CHECK 목록을 바꾸지 않으려고 append-only `tag_ticket_ledger`와 `user_balances.tag_tickets`(트리거로 갱신)를 새로 만들었다. 기존 Worker는 이 표를 몰라 먼저 적용해도 영향이 없다.
- **지급:** 마이그레이션이 활성 플레이어 전원에게 `NICKNAME_TAG_RULES.welcomeTickets`(5장)를 한 번 넣는다. reference가 고정이라 다시 돌려도 중복 지급이 없다. 지급 시점에 없던 계정은 포함되지 않으므로, 나중에 만든 계정에는 따로 넣어야 한다.
- **결제 순서:** 뽑기는 **뽑기권 → 골드** 순으로 결제한다. 수단은 한 조건부 INSERT가 `CASE WHEN tag_tickets >= 1`로 고르면서 `nickname_tags.payment`에 적고, 같은 배치의 차감 행이 그 값을 보고 골드 원장 또는 뽑기권 원장 한쪽에만 들어간다. 그래서 결제 수단을 고르려고 따로 읽지 않고, 동시에 두 번 눌러도 어느 쪽도 마이너스가 되지 않는다. 같은 요청 번호의 재시도는 처음 결과를 돌려주며 다시 차감하지 않는다.
- **화면:** 상점 타일 `뽑기권 N장`, 버튼 `뽑기 · 뽑기권 1장`, 결과 시트 `뽑기권 1장`, 아래 줄에 남은 장수. 뽑기권이 0이면 예전처럼 `뽑기 · 300G`로 돌아간다. 미리보기도 5장으로 시작해 같은 순서로 쓴다.

## 주식 뉴스 30분 슬롯과 회사 생애주기 (2026-11-05)

- **요청:** 뉴스를 30분마다(하루 18개 필수), 일부만 주가를 움직이게, 회사별 생애주기는 완전히 숨김.
- **슬롯:** 틱 번호 0, 3, …, 51(09:00~17:30). 찌라시(확인/부인은 4~8슬롯 = 2~4시간 뒤), 모기 사냥, 주가를 움직이는 뉴스 4~7개를 먼저 배치하고 남은 칸을 분위기 기사(`feature`, 효과 0)로 채운다. 주가를 움직이는 사건 수는 이전과 같아 변동성을 다시 맞출 필요가 없었다.
- **생애주기:** `shared/stock-lifecycle.ts`. 국면별로 뉴스에 나올 가중치, 호재 비율, 효과 크기 배율이 다르다(예: 위기 호재 35%, 성장기 65%). 다음 국면은 전이 확률표로 정한다. 시드는 `HMAC(STOCK_SEED_SECRET, "stock|phase")`이고 기준일은 2026-01-01이다. API·운영 탭·전환 공시 어디에도 국면을 내보내지 않는다.
- **모의실험(국면 포함, 1,000개월):** 상장폐지 0/1/2/3+ = 565/341/84/10, 평균 0.54건/월.
- **배포 당일:** 새 기사 id는 슬롯 번호를 쓴다(`news:<날짜>:s<슬롯>`). 오늘 이미 나간 예전 id와 겹치지 않는다.

## 주식 AI 엔진 선택 (2026-11-05)

- **요청:** 사용자가 OpenAI도 쓰고, Claude와 OpenAI 중 무엇을 쓸지 운영자 계정에서 고를 수 있게 해 달라고 했다. 기본값은 OpenAI.
- **설정:** `stock_settings.ai_provider`(`openai`|`anthropic`). 운영 API `PUT /api/admin/stock/ai`가 `{ enabled?, provider? }`를 받는다. 매 호출 직전에 설정을 읽으므로 바꾼 즉시(다음 08:50·18:00 묶음부터) 적용된다.
- **키 없는 엔진:** 고른 엔진의 키가 없으면 다른 엔진으로 자동 전환하지 않고 템플릿을 쓴다. 운영자가 고른 엔진과 다른 곳에 비용이 나가지 않게 하려는 것이다. 운영 탭에 엔진별 키 유무가 보인다.
- **OpenAI 요청:** `openai` 7.50.0의 `chat.completions.create`, 모델 `gpt-6.1-sol`, `reasoning_effort: 'medium'`, `max_completion_tokens` 16,000, `response_format: { type: 'json_schema', strict: true }`. 시스템 프롬프트가 맨 앞이라 OpenAI 자동 캐시가 적용된다. `message.refusal`이 있으면 거절로 보고 템플릿을 쓴다. 사용법은 설치된 SDK 타입 정의로 확인했다.
- **OpenAI 요금:** $2 입력, $10 출력(100만 토큰당). 캐시 입력은 자료에 따라 $0.10~$0.20이라 높은 쪽($0.20)으로 계산한다. 2026-11-05 기준 2차 가격 정리 페이지에서 확인했고 OpenAI 공식 가격표와 다를 수 있다. 호출 전 어림은 프롬프트 글자 수 × 입력 단가 + `max_tokens` × 출력 단가.
- **예산:** 하루 $0.80 상한과 `ai_usage` 집계는 두 엔진 합계다.

## 주식 PR 12 — AI 뉴스와 시장 열기 (2026-11-05)

- **AI 기사 저장 시점:** 08:50 묶음 호출 결과를 그 기사의 틱 시각(`publish_at`)과 함께 미리 `stock_news`에 넣는다. 틱이 같은 id로 템플릿 행을 `INSERT OR IGNORE`하므로 AI 글이 남고, 틱이 없던 행은 생기지 않는다. 미래 행은 DB에만 있고 어떤 API도 내려주지 않는다(§1-2).
- **SDK·요청 형태:** `@anthropic-ai/sdk` 1.5.0의 `client.beta.messages.create`에 `betas: ['server-side-fallback-2026-07-01']`, `fallbacks: 'default'`, `output_config: { effort: 'medium', format: { type: 'json_schema' } }`, 시스템 프롬프트 `cache_control: ephemeral`. 사용법은 Claude API 참고 문서와 설치된 SDK 타입 정의에서 확인했다. `stop_reason === 'refusal'`을 먼저 확인한다. 비스트리밍, `max_tokens` 16,000, 타임아웃 90초, 재시도 1회.
- **비용 계산:** 응답의 최상위 `usage`(입력·출력·캐시 쓰기·캐시 읽기)로 계산한다. 대체 모델이 답했으면(`response.model`이 다르면) 더 높은 Opus 요금($5/$25/$6.25/$0.50)을 적용해 과소 집계를 피한다. 호출 전 어림값은 프롬프트 글자 수를 모두 캐시 쓰기 토큰으로, 출력은 `max_tokens` 전부로 잡는다(대체 요금 기준). 이렇게 보수적으로 잡아도 하루 08:50·18:00 두 번 호출은 $0.80 안에 들어간다.
- **장 중 사건:** 게임 속보와 큰손 소식은 반영 순간에 공개되어야 하므로 AI를 기다리지 않고 템플릿을 쓴다(지시서의 "준비되지 않았으면 템플릿 즉시 공개"를 항상 적용). 밤사이 공개된 게임 결과(09:00 반영)는 08:50 묶음에 포함되어 AI가 쓴다.
- **찌라시:** 엔진의 날짜 시드 사건으로 넣어 시뮬레이션에 포함했다(모기·찌라시 포함 1,000개월: 상장폐지 0/1/2/3+ = 586/337/73/4, 평균 0.49건/월). 확인/부인 보도 시각은 찌라시 12~24틱 뒤, 같은 날 안이다.
- **큰손 제한:** 거래 기록으로 "같은 사람·종목, 지난 1시간 안의 큰손 거래"를 확인한다. 기사 id는 거래 id에서 만들어 누가 했는지 드러나지 않는다.
- **마감 화면:** 시황 요약, 본인 코멘트, 금요일 주간 실적, 내 주식·평가손익·마지막 거래일 변동을 보여 준다. 코멘트는 `audience_user_id`가 본인인 행만 내려준다.
- **시장 공개일 처리:** 0016 마이그레이션이 그때까지 정답이 있는 게임 판을 "효과 0, 반영 완료" 이벤트로 채운다. 가격 커서는 0015 적용 시각에서 시작하므로 공개 당일 09:00부터 계산된다(3일 넘게 비면 그날 0시부터).
- **운영 키:** `ANTHROPIC_API_KEY`가 없으면 템플릿만 쓴다. 운영 탭에 "AI 키 없음 · 템플릿"으로 보인다.

## 주식 PR 11 — 게임 연동 (2026-11-05)

- **즉시 반영:** 장 중 공개는 다음 10분 틱을 기다리지 않는다. 엔진에 "이벤트 단계"(그 종목만, 공개 시각에, 무작위 변동 없이 효과만)를 넣었다. 그 사이 거래는 가격 버전이 바뀌어 409로 다시 확인받는다. 모든 매매는 먼저 같은 동기화를 거치므로, 공개된 결과를 보고 옛 가격으로 사는 일이 생기지 않는다.
- **이벤트 생성 위치:** 게임 batch에 주식 쓰기를 넣지 않았다. 공개 처리가 커밋된 뒤 같은 요청에서 `advanceStocks`를 호출하고(실패해도 게임 응답은 성공), 모든 주식 조회와 Cron도 공개됐지만 이벤트가 없는 판(최근 4일)을 찾아 만든다. 판별 id는 `game:<게임>:<날짜>`이다. 첫 조회 batch에 이 확인과 미반영 이벤트 조회가 들어가 시장 조회는 3+4 = 7쿼리, "변경 없음"은 4쿼리다.
- **평소 시각:** 오늘 이전에 공개된 최근 14판의 중앙값(짝수면 가운데 두 값의 평균). 3판 미만이면 08:00:00·18:00:00. 같은 시각이면 효과 0, 기사는 `보합`.
- **모기 사냥:** DB 이벤트가 아니라 템플릿 뉴스처럼 날짜 시드로 정한다(예굼 거래일만). 1,000개월 모의실험(모기 포함): 상장폐지 0/1/2/3+ = 620/322/56/2, 평균 0.44건/월, 관리종목 1.14건/월. 게임 연동은 DB 사건이라 모의실험에 넣지 않았다(±8% 상한, 대체로 대칭).
- **출제자 제한:** 연동 종목의 미반영 게임 이벤트가 있거나, 오늘 게임이 켜져 있는데 오늘 결과가 아직 반영되지 않았으면 제한한다. 매매 API는 409 `AUTHOR_LOCKED`, 상세 화면은 버튼에 안내를 보여 준다.
- **시장 공개 전 과거 판:** 시장을 처음 열 때(PR 12) 최근 4일 판이 한꺼번에 반영되지 않도록, PR 12 마이그레이션에서 기존 공개 판을 "효과 0, 반영 완료" 이벤트로 미리 채운다.

## 주식 PR 10 — 시장 기반 (2026-11-05)

## 개선 PR 7 — 슬롯머신 (2026-11-04)

- **범위·기준:** PR #28 머지·배포 완료 알림 후 최신 main `9fc547c`에서 `codex/slot-machine`을 만들었다. 개선 지시서 §5-2 전체와 사용자 추가 지시를 따르며 지시서·확인 필요 목록의 기본값은 수정하지 않는다.

- **조회:** bootstrap 프로필·캐시·현재 주 점수 조회를 합쳐 내 정보·랭킹·게임 참가자에서 재사용한다. 세 게임의 현재 판·설정과 예측을 각각 한 쿼리로 읽으며 공개 전 정답·행운 사진을 숨기는 기존 권한을 유지한다. 과거 출제자 이름과 비활성 과거 참가자의 결과를 보존한다. 뽑기 요약은 미생성·충전 대기 코인을 계산만 하고, 실제 기계 진입·구매·플레이에서 저장한다.
- **정산·Cron:** 기존 요청 시 멱등 정산을 유지한다. 할 일 없는 예측·로또 확인은 각각 한 SELECT이며, 당일 로또 추첨이 아직 없으면 현재 규칙의 17:00 이후 최초 요청에서 만든다. PR 6의 17:30 변경을 앞당기지 않는다. 정산 전용 Cron은 추가하지 않았다. 미리 정산해도 요청의 경합·누락 복구 검사가 필요하며, 정기 폴링의 무작업 비용은 이미 제한된다. 일일 정리는 `0 15 * * *` UTC, 즉 KST 00:00 하나로 실행한다. 향후 주식 Cron을 도입할 때 같은 scheduled handler에 통합할 수 있다.
- **정리 범위:** 세션·로그인 제한 버킷은 만료된 것만, 캐치마인드는 생성 후 30일 초과 영수증 중 결과 판이 종료되고 현재 판이 아닌 것만 각 500개까지 지운다. 답변이 FK로 참조하는 guess 영수증과 진행 중 판의 영수증은 영구/진행 중 보존한다. 무조건 30일 삭제하면 실제 FK와 재시도 보호를 깨므로 이 제외 조건을 둔다. 원장·점수·그림·답변 기록은 지우지 않는다. 삭제된 비답변 영수증의 requestId 보장은 보존 기간 안으로 한정된다.
- **인증 쓰기:** 성공 로그인은 자기 이전 토큰과 사용자 제한 버킷만 정리하고 전역 만료 정리는 Cron에 맡긴다. 로그인·비밀번호 확인은 한도+1번째 실패 기록을 유지한 뒤 차단 중 같은 버킷을 계속 쓰지 않는다. 빈 RETURNING도 429로 거절하고 만료 전 창을 늘리지 않는다. 비밀번호 KDF 강도는 변경하지 않는다.
- **브라우저:** 보이는 홈·랭킹 30초, 나머지 화면 60초, 숨김·오프라인·미리보기·뽑기 폴링 중단을 적용한다. 최근 성공 조회 10초 이내 탭 복귀와 진행 중 요청의 중복을 막는다. BroadcastChannel 리더 선출은 적용하지 않는다. 현재 3~4명 예산을 만족하는 단일 탭 정책을 먼저 검증하고, 다중 탭 사용량은 탭 수만큼 늘 수 있음을 예산에 명시한다. 쓰기·계정 전환 요청의 기존 직렬화는 유지한다.
- **번들·CPU:** 운영·주식·뽑기 화면 및 미리보기 물리 엔진을 지연 로딩한다. 오프라인 미리보기 때문에 서비스 워커의 정적 파일 사전 캐시는 유지하므로 설치 시 총 다운로드 절감이라고 주장하지 않는다. PNG CRC32 표와 직접 바이트 복사로 기존 검증의 결과를 보존하며 CPU 비용을 줄인다. 비밀번호·이미지 수치는 로컬 Node 측정이며 운영 Workers CPU는 미측정이다.
- **공식 한도·측정:** 2026-11-04 공식 문서에서 Workers 100,000요청/일·CPU 10ms, D1 500만 rows_read/일·10만 rows_written/일·호출당 50회·계정 5GB를 확인했다. 추가로 무료 **DB 하나는 500MB**이고 `db.batch()`는 호출 한 번으로 센다. SQL 문장/prepare 수와 실제 binding 호출 수를 구분해 기록한다. 자세한 실제 전후 값·성장 시나리오·보류 사항은 [무료 플랜 예산](free-plan-budget.md)에 남긴다.
- **운영 반영:** 운영자의 원격 마이그레이션 → 머지 → 배포 순서다. 원장 쓰기의 컬럼·정합성은 구버전과 호환된다. 다만 마이그레이션 후 구버전 Worker가 남아 있는 동안에는 트리거가 포함된 `meta.changes` 때문에 출석 응답의 `awarded`가 false일 수 있다(골드 지급은 정상). 리뷰·배포 준비 후 순서대로 반영해 이 구간을 짧게 유지한다. 이번 작업은 로컬 검증과 Draft PR까지만 수행하며 원격 DB·secret·머지·배포는 수행하지 않는다.

## 운영 개선 PR 2 — 운영 탭과 설정 (2026-11-02 KST)

- **기반·범위:** 사용자에게 PR #18 머지 알림을 받은 뒤 최신 main `f978282`에서 `codex/admin-console`을 만들었다. PM 계획은 PR 1의 첫 커밋에 이미 보존되어 있고 변경하지 않았다. PR 2와 요청된 출석/캐치마인드 E2E 회차 의존성 보완만 진행한다.

## 예측 게임 정책 — Phase 1 확정

출제자·마감·공개 시각·배점·보상은 `shared/balance.ts`를 단일 소스로 사용한다. Worker의 지급과 화면의 도움말·결과·미리보기가 같은 값을 읽는다.

- **입력:** 기상·퇴근은 `HH:MM:SS`만 받는다. `HH:MM`은 400으로 거절한다. 화면은 시·분·초 숫자를 직접 입력하거나 조절할 수 있는 입력을 사용한다.
- **기상시간 정답:** 클라이언트 시각을 무시하고 서버 시각을 기록·공개한다. 같은 날 재요청은 조건부 쓰기로 첫 정답을 보존하며 취소할 수 없다. 확인 시트를 거치고 공개 후 버튼을 숨긴다.
- **퇴근시간 자동 공개:** 미리 입력한 실제 퇴근 시각을 뜻한다고 해석했다. 이미 지난 시간을 입력하면 즉시 공개 상태가 된다.
- **조기 공개:** 공개 순간 예측을 닫는다. 공개된 정답의 변경도 막는다.
- **참여:** 게임별 첫 저장 순간 100G를 지급한다. 예측 수정·동시 저장에는 추가 지급하지 않는다.
- **정확도:** 각 게임의 차이(시간은 초)의 상한을 위에서부터 비교해 점수를 정한다. 0점은 원장 행을 만들지 않는다.
- **1등·동점:** 점수와 무관하게 차이가 가장 작은 예측자 모두 100G를 받는다. 예측자가 없으면 지급하지 않는다.
- **출제자 부재:** 예측 마감은 적용하되 정답이 없으면 결과를 대기 상태로 둔다. 정산하지 않고 먼저 받은 참여 보상은 유지한다.
- **주간 순위:** 점수와 순위만 표시하며 주간 골드 보상은 지급·표시하지 않는다.
- **기록:** 공개된 날만 세어 오늘을 제외한 최근 3판을 조회한다. 정답이 없는 날은 건너뛴다.
- **초기 골드·점수:** 지급 정책이 없으므로 원장의 합계 0을 보여 준다. 확정된 시작 잔액이 0이라는 뜻은 아니다.
- **계정 중지:** 기록과 원장을 보존하는 비활성화로 처리한다. 재생성/비밀번호 변경/권한 변경 시 기존 세션을 폐기한다.

## 출석과 캐릭터 선택 — Phase 2 확정

- **출석 저장:** `attendance(user_id, date, streak, created_at)`의 `(user_id, date)` PK로 서버 KST 하루 한 번 저장한다. 어제 출석했으면 연속 일수에 1을 더하고, 빠진 날이 있으면 1로 시작한다. 클라이언트 날짜·연속 일수·보상은 사용하지 않는다.
- **출석 지급:** `shared/balance.ts`의 규칙으로 7일째·14일째 등 7의 배수에는 500G, 그 밖에는 100G를 지급한다. 출석과 `attendance:<date>:<userId>` 원장 행을 같은 D1 batch에 기록하며 재시도·동시 요청은 한 번만 지급한다. 자정을 넘겨 DB 쓰기가 지연된 요청은 거절하고 현재 날짜로 다시 조회한다. 운영자는 출석할 수 없다.
- **출석 화면:** 화면의 n일째와 7칸은 달력 요일이 아닌 1~7일 주기로 표시한다. 월간 기록은 월별 서버 조회이며, 내 정보의 출석 수와 홈 잔액도 서버 데이터를 사용한다.
- **홈 접힘:** 완료 상태는 “오늘 출석 완료 · n일째” 한 줄이다. 새 출석을 받으면 기존 코인·캐릭터 점프가 끝난 뒤 접는다. 펼침은 즉시 높이를 바꾸고 opacity만 전환하며 reduced motion을 지킨다.
- **기기 출석 정리:** 기존 로그인 사용자의 localStorage 출석 키는 정리하고 서버로 옮기지 않는다. 미리보기 출석은 별도의 기기 데이터로 유지한다.
- **캐릭터 저장:** nullable `users.character`에 공통 `ArtKey` 8종 중 하나를 저장한다. null이면 min→axolotl, siwon→cat, yeseo→bunny, 나머지→monkey 기본값을 사용한다. 같은 캐릭터를 여러 플레이어가 선택할 수 있다. bootstrap과 공개 결과에 캐릭터를 포함해 랭킹·과거 기록의 아바타도 서버 선택을 따른다.
- **선택 이관:** 서버 값이 null일 때만 현재 기기의 기존 선택을 조건부로 한 번 가져온다. 이미 서버 값이 있으면 그대로 보존한다. 요청에 예상 사용자 ID를 검사해 다른 탭의 계정 변경이 이전 사용자의 선택을 새 계정에 가져오지 못하게 한다. 성공 후 기존 키를 지우고, 실패 시 재시도를 위해 보존한다. 미리보기 선택은 별도 localStorage 키를 사용한다.
- **예측 도움말 보완:** `SCORE_TABLES`의 차이 값을 시간·분·초로 변환해 “1분 이내”, “1시간 이내”처럼 표시한다. 행운 점수는 “N점 차이 이내”, 0은 기존 “정확히 일치”를 사용한다. 배점이나 기준값을 중복 정의하지 않는다.

## 상점 경제 — Phase 3 확정

- **공통 규칙:** 쿠지 가격·등급 수량·보상, 데일리 로또 추첨 시각·숫자 범위·당첨금, 스피또 확률·가격·당첨금은 `shared/balance.ts`에서 서버·화면·미리보기가 함께 읽는다.
- **구매와 이용권:** `shop_purchases`의 사용자별 고유 `requestId`로 구매를 식별한다. 조건부 쓰기에서 잔액·이용권·사용자 상태·서버 시각을 검사하고, 새 구매 ID에 종속된 차감·지급을 같은 D1 batch에 넣는다. 같은 요청은 저장된 결과를 돌려주며 다른 상품·내용으로 재사용하면 거절한다. 이용권은 수정·삭제를 막은 `inventory_ledger`의 합계다. 운영자는 구매할 수 없다.
- **예굼쿠지:** 모든 플레이어가 같은 100장 판을 사용하며 서버 crypto 난수로 등급을 섞는다. 미판매 칸의 등급은 응답에 넣지 않는다. 당일 개인 구매 수를 DB 쓰기 안에서 계산해 5장까지 300G, 6장째부터 400G로 차감한다. 여러 장 중 하나라도 판매됐거나 잔액이 부족하면 전부 실패한다. A~D는 점수·골드, E~H는 해당 이용권, 마지막 구매는 라스트원 1,000G를 추가 지급한다. 모두 팔린 다음 요청에서 새 판을 만든다. 점수 주차는 구매한 KST 날짜의 월요일이다.
- **데일리 로또:** 서로 다른 1~25 숫자 5개를 500G 또는 이용권 1장으로 산다. KST 17:00 전에는 당일, 이후에는 다음 날 추첨 표가 된다. 추첨 날짜 PK로 번호를 한 번만 저장하고 5/4/3/2개 일치에 5,000/3,000/1,000/500G를 지급한다. 구매 수 제한은 없다. 지난 미정산 날짜도 bootstrap·상점 요청에서 추첨·정산하며 같은 표에 두 번 지급하지 않는다. bootstrap은 잔액·내역 조회 전에 로또 정산을 완료하므로 상점을 열지 않아도 첫 응답에 당첨금이 반영된다.
- **스피또:** 300G 또는 이용권 1장을 사용한다. 서버 crypto 난수로 구매 순간 10% 당첨 여부와 기존 3칸 배치를 저장한다. 당첨은 같은 캐릭터 3개, 낙첨은 3개가 일치하지 않으며 당첨금 1,500G를 구매 batch에서 지급한다. 긁기·나가기·재접속은 결과나 잔액을 바꾸지 않는다.
- **요청 경계:** 본문을 읽은 후 서버 시각을 잡고 DB 쓰기에서도 날짜·추첨 회차 경계를 검사한다. 응답이 유실된 구매는 기기의 사용자별 세션 저장소에 같은 요청 내용을 보관해 재확인한다. 성공한 구매는 후속 잔액 조회가 실패해도 실패로 바꾸지 않는다.
- **화면:** 상점·로또·스피또에 이용권 수량과 결제 선택을 표시한다. 쿠지 등급·라스트원 보상은 기존 시트 스타일의 모달로 안내하며 닫기·바깥 클릭·Esc를 지원한다. 미리보기는 독립적인 메모리 상태로 서버 없이 같은 경제 규칙을 체험한다. 미리보기의 출석 보상과 상점 결제는 같은 잔액을 사용하며 날짜가 바뀌어도 이미 받은 보상을 회수하지 않는다.

## 캐치마인드 — Phase 4 확정

- **판과 차례:** 날짜를 바꾸어도 진행 중인 판을 유지한다. 처음에는 플레이어 누구나 차례를 맡을 수 있으며, 그 뒤에는 정답자에게 다음 차례가 넘어간다. 오답 6개 또는 출제자의 직접 종료에는 보상 없이 기존 출제자가 차례를 유지한다. 끝난 판은 결과로 남겨 두고 다음 출제자가 새 판을 시작할 때 교체한다. 운영자는 조회만 한다.
- **제시어:** `shared/catchmind-words.ts`의 400개는 기존 [skatch-mind-words.js](https://github.com/iam-yeseo/yegoom/blob/main/src/lib/skatch-mind-words.js)에서 가져왔다. 원본 blob은 `4c4b07dc9e46e03da98434965e293d9c6c81e9d4`다. 서버 crypto 난수로 선택하고 출제자에게만 전달한다. 공개 전에 3회 바꿀 수 있으며 같은 판에서 이미 받은 단어는 다시 나오지 않는다. `wordVersion` 검사는 바꾸기 전 제시어로 작성한 그림의 뒤늦은 저장을 막는다. bootstrap에는 공개 전 정답과 그림을 넣지 않는다.
- **답과 정산:** 공백만 제거해 비교하며 대소문자나 유니코드 정규화 규칙을 추가하지 않는다. 답변은 모두 공개되고 오답 3개부터 첫 글자·글자 수 힌트를 보여 준다. 첫 정답자에게 힌트 여부와 무관하게 3점·5G를 지급한다. 요청 기록·답변·종료·다음 차례·원장 지급을 한 D1 batch에 묶는다. 같은 `requestId`는 오답 횟수나 보상을 늘리지 않고, 다른 내용으로 재사용하면 거절한다. 동시 정답에서도 한 사람만 지급받는다. 원장 reference는 `catchmind:score:<roundId>`, `catchmind:gold:<roundId>`다.
- **게임 날짜:** 날짜 구분 없이 이어지는 판의 점수 기준일은 그림을 공개한 서버 KST 날짜로 정한다. 다음 주에 정답을 맞혀도 그 날짜가 속한 월요일을 `week_start`로 사용한다. 일별 점수 그래프도 지급일 대신 공개일에 합산한다. 출제 본문을 읽은 뒤 서버 시각을 잡고 SQL에서도 날짜 경계를 확인한다.
- **그림:** 공개한 그림은 수정할 수 없다. PNG 또는 WebP data URL을 저장하며 “300KB”는 디코딩된 이미지 바이트 300KiB(307,200바이트)로 적용한다. 큰 JSON 본문 허용은 출제 경로에만 한정한다. 선언된 MIME과 실제 PNG/WebP 서명·청크·정사각형 양수 크기를 확인하고, PNG 청크 CRC도 검사한다.
- **도구와 컬러 피커:** 의존성을 추가하지 않고 펜·지우개·스캔라인 영역 채우기·실행 취소를 구현한다. 컬러 피커는 가로 채도·세로 명도, 색상, 투명도, HEX 입력, 견본·최근 색 5개를 제공하며 포인터·터치·키보드를 지원한다. 투명도는 펜에 적용하고 채우기는 불투명으로 처리한다. 브라우저 지원 범위 때문에 스포이드는 넣지 않고, RGB/CSS/HSL 출력 형식 선택도 제외한다. 캔버스와 피커의 `data-notouchfx`는 전역 터치 이펙트에서 제외한다.
- **갱신과 미리보기:** 화면이 보이는 동안 5초마다 조회하고 숨겨지면 멈춘다. `#/preview`는 서버 없이 독립 상태로 같은 판 진행을 체험하며 실제 사용자 기록·원장에 쓰지 않는다. 기존 디자인 토큰과 reduced motion 규칙을 유지한다.

## 전역 터치 이펙트 — Phase 5 확정

- **표현과 설치:** `src/motion.ts`의 `installTouchEffect()`를 버튼 눌림 피드백과 함께 한 번 설치한다. 크림색 바탕의 가시성을 위해 채운 원을 2px 코랄(`#FF8E7A`) 테두리 링으로 바꾸고 시작 불투명도를 0.7로 높였다. 앱 팔레트 색 점 4개는 6px이며 기존 `fxLayer()`에서 전체 크기 최대 44px, 수명 400ms 이하를 유지한다. transform·opacity만 움직인다. 기본 대화상자 안에서는 해당 효과만 임시 manual popover로 올려 가려지지 않게 하며 포커스와 클릭은 그대로 통과시킨다.
- **입력과 제한:** 주 포인터의 `pointerdown`만 받으며 마우스는 왼쪽 버튼만 허용한다. passive 리스너로 스크롤·드래그를 방해하지 않는다. 60ms 이내 연속 입력을 무시하고 동시에 남는 이펙트는 최대 8개로 제한한다.
- **제외:** reduced motion에서는 노드를 만들지 않는다. `input`, `textarea`, `select`, `canvas`, `[contenteditable]`, `[data-notouchfx]`와 내부 요소에서도 만들지 않아 입력·그림·피커 조작을 유지한다.
- **캐치마인드 이미지 보완:** 저장된 data URL은 유지하되 상태 응답의 `image`에는 판 ID별 URL만 넣는다. `GET /api/catchmind/rounds/:id/image`는 로그인과 공개 전 출제자 권한을 검사한 뒤 PNG/WebP 바이트를 반환한다. `Cache-Control: private, max-age=31536000, immutable`로 바뀌지 않는 그림을 브라우저 HTTP 캐시에서 재사용하고 `Vary: Cookie`로 로그인 세션별 캐시를 구분한다. 서비스 워커의 `/api` 캐시 제외 규칙은 그대로 유지한다. 미리보기의 로컬 그림은 서버에 요청하지 않는다.

- **닉네임:** 원본 `normalizeNickname`과 같은 NFC·trim·한글/영문/숫자·grapheme 1~10글자를 사용한다. `users.display_name`을 바꾸고 `username`은 로그인·권한·캐릭터 식별·기기 저장소 키에 유지한다. 노출되는 이름과 출제자 표시는 현재 닉네임을 사용한다. SQL 조건부 UPDATE와 활성 사용자 `COLLATE NOCASE` 유니크 인덱스가 동시 중복을 막는다.
- **프로필 사진:** 원본 photo picker의 EXIF 디코딩·사각형 선택 방식을 참고해 드래그·핀치·슬라이더 자르기를 구현했다. 512px 정사각형, WebP 우선/JPEG 대체, 실제 바이트 260KiB 제한이다. `user_photos`에 BLOB을 저장하고 `users.photo_version` 카운터를 올린다. 삭제해도 카운터를 보존·증가시켜 예전 immutable URL을 재사용하지 않으며, 사진이 없으면 API의 `photoVersion`은 null이다.
- **계정 전환:** 프로필 화면을 사용자 ID별로 다시 만들어 이전 계정의 편집 초안을 버린다. 프로필 변경 API에는 화면의 `expectedUserId`를 보내며 다른 탭에서 세션 쿠키가 바뀌었으면 409로 거절해 새 계정에 이전 초안이 저장되지 않게 한다.
- **이미지 검증·캐시:** 서버에서 base64·실제 WebP/JPEG 컨테이너·치수·바이트 제한을 검증한다. 버전과 본문을 일치시켜 조회하고 로그인·공개 권한을 유지한다. HTTP 캐시는 private/1년/immutable 및 `Vary: Cookie`를 사용하며 오류·JSON은 no-store다. 프로필과 행운 사진 본문은 폴링 응답에 포함하지 않는다. Workers에 픽셀 디코더가 없으므로 서버는 형식·프레임 경계·메타데이터를 검사하고 실제 디코딩은 브라우저가 수행한다.
- **전역 표시:** 원형 Avatar는 프로필 사진을 우선한다. 홈 방·히어로·시상대·로그인·프로필 큰 캐릭터·캐릭터 선택은 캐릭터를 유지한다. 과거 결과·캐치마인드 응답도 사진 버전과 닉네임을 반환한다. 중지된 대상의 과거 프로필 사진은 로그인한 활성 사용자에게 계속 보이며, 중지된 사용자 본인은 접근·수정할 수 없다.
- **당첨 알림:** 스피또 당첨과 로또 1~3등 지급을 실제 지급 원장 행에서 읽어 동일 batch에 알림을 INSERT한다. 지급 reference 기반 UNIQUE가 재시도·동시 정산을 보호한다. 최근 10분의 전역 최신 5건을 먼저 제한하고 본인을 제외하므로 반환 수는 5개 이하다. 사용자별 localStorage에 실제 표시한 ID를 기록하고 4초씩 순서대로 보여 준다. 클릭 닫기, polite status, reduced motion 200ms 페이드만 제공하고 미리보기 가짜 알림은 없다.
- **행운 증거:** 별도 사진 PUT은 당일 활성 출제자만 가능하며 SQL 쓰기 시각과 공개 여부를 함께 검사한다. 새 정답 저장은 사진이 필수이고 조건부 저장에서도 존재를 확인한다. 사진은 긴 변 1280px·440KiB 이하 WebP/JPEG이며 원본 비율을 유지한다. 공개 전 교체할 때 버전을 올리고 공개 후에는 고정한다. 출제자는 항상, 나머지는 공개 후에만 조회한다. 오늘 결과·최근 3판에서 확대 보기·닫기·Esc를 지원한다. 기존 사진 없는 과거 판은 계속 읽을 수 있다.
- **미리보기:** 프로필·사진은 해당 미리보기 메모리에서만 바꾸며 실제 API를 호출하지 않는다. 행운 미리보기는 실제 사용자 yeseo의 출제 흐름으로 사진 선택·점수 저장·공개까지 체험하고 보상은 만들지 않는다. 과거 예시 사진은 ‘미리보기 증거’라고 표시한 로컬 그림을 사용한다.
- **초기화:** `announcements`, `luck_photos`를 삭제 대상에 더해 19개 기록 테이블을 비운다. `user_photos`와 사용자 닉네임·사진 버전을 포함한 계정/세션/설정은 보존한다. 사전 검사와 초기화 도구는 별도이며 자동 이름 변경이나 개발 중 운영 초기화는 없다.

## 사용자 비밀번호 변경 (2026-11-02)

- `PUT /api/me/password`는 Origin·로그인·활성 사용자 확인 후 현재 비밀번호를 확인한다. 운영자도 같은 경로로 자신의 비밀번호를 바꾼다. 브라우저는 기존 프로필 수정과 같이 `expectedUserId`를 함께 보내 계정이 바뀐 탭의 저장을 거절한다.
- `shared/password.ts`에서 새 비밀번호 12~128자(로그인/CLI와 같은 UTF-16 길이), 필드 UTF-8 512바이트, 요청 본문 2,048바이트 상한을 공유한다. 공백 제거·정규화는 하지 않는다. 동일한 비밀번호를 거절하고 비밀번호나 해시를 응답·로그에 넣지 않는다.
- 사용자별 `hashToken("password:" + userId)` 버킷으로 15분에 10회 확인을 허용한다. 동시 요청도 비싼 확인 전에 SQL upsert로 슬롯을 확보한다. 실패 시 유지하고 성공한 변경 batch에서 버킷을 지운다. 11번째부터 429이며 차단 중에는 KDF를 실행하지 않고 창을 연장하지 않는다.
- 확인한 해시와 요청 세션을 조건으로 `users UPDATE → 새 sessions INSERT → 시도 버킷 DELETE`를 하나의 D1 batch로 처리한다. 기존 `users_revoke_sessions` 트리거가 다른 세션을 지우며 `changes()` 조건으로 패배한 동시 요청이 세션을 만들지 못하게 한다. 비활성화·로그아웃·중복 변경과 경합하면 409, 새 세션 생성 실패는 해시와 세션 삭제까지 롤백한다. 성공 응답은 새 HttpOnly·SameSite=Strict 쿠키를 설정한다.
- 내 정보 시트에는 숨은 로그인 아이디, `current-password`/`new-password` 자동완성, 개별 보기/숨기기, 길이·동일값·확인 일치 안내를 둔다. 닫기·바깥 누르기·Esc와 포커스 이동을 지원하며 저장 중 중복 제출/닫기를 막는다. 닫으면 입력 상태를 버리고 미리보기에서는 항목을 비활성화해 API를 호출하지 않는다. 비밀번호 분실은 운영자 CLI 초기화로 안내한다.
- 성공 경로는 PBKDF2 확인 1회+생성 1회, 로그인은 확인 1회다. 통합 테스트에서 실제 Worker 번들의 호출 수를 측정하며 `node scripts/measure-password-cpu.mjs`로 같은 암호 함수의 로컬 Node WebCrypto CPU를 별도로 측정한다. 30회 CPU 중앙값은 로그인 26.780ms, 변경 54.218ms(약 2.02배)다. 운영 Workers CPU 측정값이 아니며 환경·p95·화면 자료는 [검증 보고](password-change-validation.md)에 기록했다.
- 마이그레이션 없음. 반영 순서는 리뷰 → 머지 → 배포이며 `npm run db:migrate:remote`는 필요 없다. 이번 작업은 Draft PR에서 멈춘다.

## 저장과 정산의 경계

`users`, `sessions`, `login_attempts`, `game_rounds`, `predictions`, `attendance`, `ledger`를 분리했다. 세션 토큰은 서버에 SHA-256 해시만 저장하고 비밀번호는 무작위 salt를 사용하는 PBKDF2로 저장한다. API 상태·오류 응답은 `no-store`이며, 캐치마인드 이미지에만 위 private HTTP 캐시 정책을 적용한다. 수정 요청은 Origin 검사와 서버 권한 검사를 통과해야 한다.

골드·점수 원장은 append-only이며 각 지급에 중복 방지용 UNIQUE `reference`를 둔다. 예측은 `predict:<game>:<date>:<userId>`, 정확도 점수는 `score:<game>:<date>:<userId>`, 1등은 `first:<game>:<date>:<userId>`다. `INSERT OR IGNORE`와 D1 batch로 중복을 막고 정정은 반대 방향의 새 행으로 기록한다. 정산의 지급 행과 `settled_at` 표시는 한 batch에 기록한다.

bootstrap·게임·기록 조회는 공개된 미정산 판을 멱등 정산한다. 늦게 조회한 과거 판도 대상이며, 점수 행의 `week_start`는 반드시 **게임 날짜가 속한 KST 월요일**이다. bootstrap은 정산 후 잔액·순위·내역을 읽으므로 첫 조회에도 지급 결과가 보인다. 새 주가 되어도 골드나 이전 결과를 삭제하지 않는다.

Phase 1의 `0002`는 정산 표시, Phase 2의 `0003_attendance_characters.sql`은 출석 테이블과 nullable 캐릭터 컬럼, Phase 3의 `0004_shop_economy.sql`은 상점 경제 테이블을 추가했다. Phase 4의 `0005_catchmind.sql`은 판·차례·답변·요청 기록 테이블을 추가했다. Phase 5는 스키마 변경이 없었다. Phase 6은 `0006_claw.sql`로 설정·계정·플레이·코인 구매 테이블만 추가하며 기존 `0001`~`0005`는 수정하지 않는다. 운영자가 `0005`까지 적용한 상태에서 **리뷰 → 운영자가 머지 전 원격 마이그레이션 적용 → 머지 → 배포** 순서로 반영한다. 이번 작업은 Draft PR에서 멈추며 원격 DB 변경·머지·배포를 실행하지 않는다.

이번 Phase에서 구현하지 않는 범위는 다음과 같다. 후속 Phase에서 확정된 항목은 `plan-v2.md`를 따른다.

- 초기 잔액·월간 보상
- 인형 도감·수집·다른 사람 기계 구경, 주식 종목·공휴일 캘린더·시세·정산
- 여섯 번째 정규 게임
- 캐릭터의 최종 애니메이션 도구와 방 꾸미기 범위
- 비밀번호 찾기, 로그인 추가 보안 정책

쿠지의 조건부 구매 기록과 후속 쓰기는 기존 `iam-yeseo/yegoom`의 `src/lib/kuji.js`, `src/routes/kuji.js`, `src/lib/shop.js`에서 패턴을 참고했다. 코드를 통째로 옮기거나 그 저장소의 다른 경제 규칙을 가져오지 않았다.

## 화면에 표시하는 잠정값

예측 게임·출석·쿠지·데일리 로또·스피또·캐치마인드는 서버의 실제 규칙으로 표시하고 원장에 지급한다. 주간 순위 보상 표시는 제거했다. 캐릭터 뽑기의 이전 위치 판정·잠정 비용·일일 횟수는 새 구현으로 교체했다. 주식 화면은 기존 코드를 유지하되 런칭 시점에는 `FEATURES.stock`으로 진입을 막는다. `src/sample.ts`의 `BALANCE`는 미리보기용으로 유지하되 예측 게임·출석·상점·캐치마인드와 겹치는 값은 `shared/balance.ts`를 참조한다.
