# 예굼방 아케이드 3 — 2차 개발 계획 (Codex 작업 지시서)

이 문서는 PM이 확정한 2차 개발 범위와 규칙이다. **Phase 단위로 하나씩** 진행한다. 한 Phase가 끝나면 Draft PR을 열고 멈춘다. PM 리뷰와 머지 후에 다음 Phase 지시를 받는다. 문서에 없는 기능 추가, 리디자인, 리팩터링은 하지 않는다. 판단이 필요하면 추측하지 말고 멈춘 뒤 보고한다.

---

## 0. 공통 규칙 (모든 Phase에 적용)

### 0-1. 범위 밖 (이번 2차 전체)
- 캐릭터 모션 개선 (나중에 따로 진행)
- 운영자 웹 화면 (계속 CLI 사용)
- 주식 시장 서버 기능 (화면 단계 유지. 규칙이 정해지지 않음)
- 캐릭터 뽑기 서버 기능 (화면 단계 유지. 아래 "보류 사항" 참고)
- 주간 순위 보상 지급 (지급하지 않음. 화면에서 보상 금액 표시를 뺀다. Phase 1에서 처리)

### 0-2. 단일 규칙 소스
- 점수표, 보상, 가격, 확률, 마감 시각은 **`shared/` 아래 한 파일**(예: `shared/balance.ts`)에만 둔다. Worker의 지급 로직과 화면의 도움말·안내 문구가 같은 값을 읽어야 한다.
- 지금 `src/sample.ts`의 `BALANCE`는 미리보기 데이터용으로만 남긴다. 실제 값과 겹치는 항목은 `shared` 값을 참조하도록 바꾼다.

### 0-3. 돈(골드)·점수 처리 원칙
- 모든 지급·차감은 기존 `ledger`(append-only)에 행으로 남긴다. 수정·삭제는 하지 않는다. 정정은 반대 부호 행으로 한다.
- 모든 지급에는 의미가 드러나는 고유 `reference`를 붙인다(예: `predict:wake:2026-11-02:<userId>`). 같은 지급이 두 번 들어가지 않도록 `INSERT OR IGNORE`와 UNIQUE에 기대어 **멱등**하게 만든다.
- 골드 차감은 잔액 검사와 차감을 **한 번의 조건부 쓰기**(D1 batch, `INSERT ... SELECT ... WHERE 잔액 >= 비용`)로 처리한다. 잔액이 음수가 되면 안 된다.
- 구매 요청에는 클라이언트가 만든 `requestId`를 받는다. 같은 요청이 두 번 와도 한 번만 처리한다.
- 참고 구현: `iam-yeseo/yegoom`의 쿠지·스캐치마인드 라우트에 요청 ID, 조건부 D1 batch, UNIQUE 패턴이 있다. 접근할 수 있으면 참고하고, 코드는 통째로 옮기지 않는다.
- 점수(`currency='score'`) 행의 `week_start`는 **그 게임이 속한 날짜의 KST 주(월요일)**로 정한다. 지급 시각 기준이 아니다.
- 지급·차감 시각과 날짜 판단은 모두 서버의 KST 기준이다. 클라이언트 시각은 믿지 않는다.
- 운영자(`role='admin'`)는 게임·출석·구매에 참여하지 않는다.

### 0-4. DB 마이그레이션
- 스키마 변경은 `migrations/000N_*.sql` 새 파일로만 한다. 기존 파일은 수정하지 않는다.
- **추가형(backward compatible)**으로 만든다. 새 테이블·새 nullable 컬럼만 추가한다. 이렇게 하면 운영자가 머지 **전에** `npm run db:migrate:remote`를 먼저 실행해도 현재 배포가 깨지지 않는다.
- PR 본문 맨 위에 "머지 전에 `npm run db:migrate:remote` 실행 필요" 여부를 적는다.

### 0-5. 작업 방식
- Phase마다 최신 `main`에서 브랜치 `codex/v2-p<N>-<짧은이름>`을 만든다. Draft PR을 열고 머지·배포는 하지 않는다.
- 커밋은 레포 스타일(영어, 명령형)을 따르고 의미 단위로 나눈다.
- 검증은 매번 아래 명령을 실행하고, 결과를 보고에 넣는다.
  ```bash
  npm run check
  npm run test:e2e
  ```
- 서버 규칙(지급액, 경계값, 동점, 멱등, 동시 요청, 잔액 부족, 마감)은 `tests/integration.test.ts`에 통합 테스트로 추가한다.
- 화면은 `#/preview`(미리보기)와 실제 로그인 양쪽에서 390px·560px(PC) 폭으로 확인하고 스크린샷을 보고에 첨부한다. 미리보기는 서버 없이 동작해야 한다. 미리보기 데이터도 새 규칙에 맞게 고친다.
- `prefers-reduced-motion`과 기존 모션 규칙(`docs/design.md`의 "모션" 절)을 지킨다.
- Cloudflare PR 미리보기 빌드 실패는 설정 문제이므로 무시하고 보고만 한다.
- 문서: Phase마다 `README.md`의 "현재 동작"과 `docs/decisions.md`의 해당 항목을 갱신한다.

### 0-6. 보고 형식 (Phase마다)
1. 구현 요약과 변경 파일
2. 마이그레이션 유무와 운영 반영 순서

4. 스크린샷 (390px, 560px)

## Phase 1 — 예측 게임 개편과 정산 (기상·퇴근·행운 점수)

**시작할 때 이 문서 전체를 `docs/plan-v2.md`로 레포에 커밋한다.** 이후 Phase는 이 파일을 기준으로 진행한다.

### 1-1. 입력 단위
- 기상·퇴근 시간은 **초 단위** `HH:MM:SS`(24시간제)로 예측하고 정답도 초 단위로 저장한다. `worker/rules.ts`의 `validValue`, `valueDifference`, 마감 계산을 초 단위로 바꾼다. 차이는 초 단위 절댓값이다.
- 행운 점수는 지금처럼 0~100 정수다.
- 실서비스 DB에는 아직 예측 기록이 없다. 그래서 `HH:MM` 하위 호환은 필요 없다. 다만 `HH:MM`이 들어오면 400 오류로 거절한다.
- 입력 UI: iOS Safari의 `<input type="time" step="1">`은 초를 고르지 못한다. 그래서 네이티브 time input에 기대지 말고 **시·분·초를 각각 조절하는 입력**을 앱 디자인 톤으로 만든다(기존 예측 입력 화면의 큰 숫자 표시와 스테퍼 스타일 유지). 키보드로 숫자를 바로 입력할 수 있어야 하고, 접근성 이름(시, 분, 초)을 단다.

### 1-2. 마감과 출제자
| 게임 | 출제자 | 예측 마감(KST) | 정답 확정·공개 |
| --- | --- | --- | --- |
| 기상시간 | min | 10:30:00 | 출제자가 **"기상했어요"** 버튼을 누른 순간의 서버 시각(초 단위)이 정답이 되고 **즉시 공개**된다 |
| 퇴근시간 | siwon | 17:00:00 | 출제자가 퇴근 시각을 **미리 초 단위로 입력**한다. 그 시각이 되면 자동 공개된다. 출제자는 공개 전까지 시각을 고칠 수 있고, "지금 공개"로 조기 공개할 수 있다(지금 동작 유지) |
| 행운 점수 | yeseo | 17:00:00 | 출제자가 점수와 힌트를 입력한다. 18:00 자동 공개, 조기 공개 가능(지금 동작 유지) |

- 정답이 공개되는 순간 예측은 닫힌다(지금 규칙 유지).
- "기상했어요"는 되돌릴 수 없다. 확인 단계(시트 또는 길게 누르기)를 한 번 거친다. 이미 공개된 날에는 버튼을 보이지 않는다.
- "기상했어요" 처리는 서버에서 한다. 클라이언트가 보낸 시각은 쓰지 않는다. 같은 날 두 번 눌러도 처음 값만 남는다(조건부 UPDATE).

### 1-3. 출제자 전용 화면
출제자로 로그인해서 자기 게임에 들어가면, 예측 입력 대신 **출제자 화면**을 보여 준다.
- 공통: 오늘 날짜, 예측 마감 시각, 참여자별 제출 여부(공개 전에는 값 숨김), 공개 후에는 결과 화면과 같은 순위표
- 기상시간: 화면 중앙에 큰 "기상했어요" 버튼과 현재 시각(초 단위로 갱신)
- 퇴근시간: 시·분·초 입력, 저장, "HH:MM:SS에 자동 공개" 안내, "지금 공개" 버튼
- 행운 점수: 0~100 점수 입력, 힌트(200자) 입력, "18:00 자동 공개" 안내, "지금 공개" 버튼
- 출제자는 자기 게임을 예측할 수 없다(지금 규칙 유지).
- 출제자 화면도 기존 디자인 토큰과 카드 스타일을 쓴다. 새 색이나 폰트를 추가하지 않는다.

### 1-4. 점수표 (차이 ≤ 기준이면 그 점수, 위에서부터 판정)
- **기상시간**: 0초 30점 · 60초 25점 · 3분 20점 · 10분 15점 · 30분 10점 · 1시간 5점 · 2시간 3점 · 그 밖 0점
- **퇴근시간**: 0초 30점 · 15초 25점 · 30초 20점 · 1분 15점 · 3분 10점 · 5분 5점 · 10분 1점 · 그 밖 0점
- **행운 점수**: 0 30점 · 1 25점 · 2 20점 · 3 15점 · 4 10점 · 5 5점 · 10 3점 · 15 1점 · 그 밖 0점

예: 기상 차이 61초는 20점, 60초는 25점이다. 행운 점수 차이 7은 3점이다.

### 1-5. 골드
- **참여 보상**: 그날 그 게임에 **처음 예측을 저장하는 순간** 즉시 100G를 준다. 예측을 고쳐도 다시 주지 않는다. reference는 `predict:<game>:<date>:<userId>`.
- **1등 보상**: 점수와 상관없이 정답과 차이가 가장 작은 사람에게 100G를 준다. **동점이면 동점자 모두**에게 준다. 예측한 사람이 없으면 지급하지 않는다.
- 점수와 1등 보상은 **정답이 공개된 판**에 대해 지급한다. reference는 `score:<game>:<date>:<userId>`, `first:<game>:<date>:<userId>`이다. 0점이면 점수 행을 만들지 않는다(ledger는 0을 허용하지 않음).
- **정산 시점**: 자동 공개는 요청이 올 때 판정된다. 그래서 정산은 "공개된 판인데 정산 기록이 없으면 정산"하는 **멱등 함수**로 만든다. bootstrap·게임 조회·결과 조회 때마다 호출해도 한 번만 지급되어야 한다. `game_rounds`에 nullable `settled_at` 컬럼을 추가해서 표시한다(지급 자체의 중복 방지는 reference UNIQUE가 책임진다).
- 출제자가 정답을 끝내 입력하지 않은 판은 정산하지 않는다(지금처럼 결과 대기). 참여 보상 100G는 이미 지급됐으므로 그대로 둔다.

### 1-6. 화면
- **결과 기록**: 각 예측 게임 화면 하단에 **최근 3판**의 기록을 보여 준다. "판"은 정답이 공개된 날만 센다. 진행되지 않은 날(정답 없음)은 건너뛰고 공개된 날 기준으로 3개를 채운다. 오늘 판은 위쪽 메인 영역에 있으므로 기록에서 제외한다.
  - 한 판에 날짜, 정답, 참여자별 예측값·차이·점수·1등 표시를 넣는다.
  - API: `GET /api/games/:id/history` → 최근 3판. 공개된 판만 응답한다.
- **도움말**: 각 예측 게임 화면 맨 아래에 "게임 방법" 아코디언을 넣는다. 기본은 접힌 상태다. 펼치면 마감·공개 방식, 참여 100G, 1등 100G, 위 점수표가 나온다. 표는 `shared` 규칙에서 생성한다(문구에 숫자를 하드코딩하지 않는다).
- 결과 화면의 점수·골드 칩은 실제 지급 규칙의 값으로 바꾼다(지금은 `BALANCE.predictionPoints` 같은 임시값).
- **주간 순위 보상 표시 제거**: 랭킹·홈 등에서 3,000/1,800/1,000G 보상 표시를 뺀다. 주간 점수와 순위는 계속 보여 준다.
- 홈의 골드, 주간 점수, 내 정보의 골드·점수 내역이 ledger 실제 값으로 나오는지 확인한다.

### 1-7. 테스트 (필수)
- 점수표 경계값: 각 게임의 기준값과 기준값+1
- 참여 100G: 첫 저장 1회, 수정 시 미지급, 동시 2회 저장 시 1회만
- 1등: 단독, 동점 2명, 예측자 0명
- 정산 멱등: 같은 판을 여러 번 조회해도 1회 지급, 자동 공개 시각이 지난 뒤 첫 조회에서 지급
- 기상했어요: 서버 시각 사용, 두 번 눌러도 처음 값 유지, 출제자 외 403, 공개 후 예측 거절
- `HH:MM` 거절, `HH:MM:SS` 범위 검사
- 점수 행의 `week_start`가 게임 날짜 기준인지(일요일 밤 판이 다음 주로 넘어가지 않는지)

## Phase 2 — 출석 서버화, 홈 출석 접힘, 캐릭터 선택 서버 저장

### 2-1. 출석
- 지금 `src/attendance.ts`는 기기별 localStorage다. 서버 저장으로 바꾼다. 테이블 `attendance(user_id, date, streak, created_at)`, PK `(user_id, date)`.
- 하루 한 번 "받기"로 출석한다(KST 날짜).
- **보상**: 연속 출석 일수 `n`을 센다(어제 출석했으면 어제 n+1, 아니면 1). `n % 7 == 0`인 날(7일째, 14일째, …)은 **500G**, 그 밖의 날은 **100G**. reference `attendance:<date>:<userId>`.
- 하루라도 빠지면 연속 일수가 1로 돌아간다.
- 화면의 "n일째"와 7칸 진행 표시는 7일 주기(1~7)로 보여 주고, 7일째 칸에 500G를 표시한다.
- 출석 화면(`src/screens/Attendance.tsx`)의 월간 기록도 서버 데이터로 바꾼다.
- 기존 localStorage 출석 기록은 서버로 옮기지 않는다(신뢰할 수 없음). 키는 정리한다.

### 2-2. 홈 출석 카드 접힘
- 오늘 출석을 마치면 홈의 출석 카드는 **접힌 한 줄**("오늘 출석 완료 · n일째" + 펼침 아이콘)이 된다. 누르면 아코디언으로 펼쳐진다.
- 접힘·펼침은 높이를 직접 애니메이션하지 않는다. 기존 모션 규칙(transform·opacity만)을 지키며 자연스럽게 처리한다(예: `grid-template-rows` 전환은 레이아웃 애니메이션이므로 쓰지 않는다. 내용 페이드와 즉시 높이 변경을 조합한다).
- 출석을 받는 순간의 연출(코인 날아가기, 캐릭터 점프)은 그대로 둔다. 연출이 끝난 뒤에 접힌다.

### 2-3. 캐릭터 선택 서버 저장
- `users`에 nullable `character` 컬럼을 추가한다. 값은 `ArtKey` 8종 중 하나다. null이면 지금의 기본 매핑(min→axolotl, siwon→cat, yeseo→bunny, 그 밖→monkey)을 쓴다.
- `PUT /api/me/character`로 바꾼다. 다른 플레이어와 같은 캐릭터를 골라도 된다(지금 동작 유지).
- bootstrap의 플레이어 목록에 각자의 캐릭터를 넣어서, 랭킹·결과·아바타가 모든 기기에서 같게 보이게 한다.
- 한 번만 하는 이관: 서버 값이 null이고 이 기기 localStorage에 선택값이 있으면 그 값을 서버에 한 번 보낸다. 그 뒤 localStorage 키를 지운다.
- 미리보기 모드는 지금처럼 기기 안에서만 동작한다.

## Phase 3 — 상점 경제 (예굼쿠지, 데일리 로또, 스피또, 이용권)

### 3-1. 이용권(인벤토리)
- 무료 로또 이용권, 스피또 이용권을 담는 append-only 테이블 `inventory_ledger(id, user_id, item, amount, reason, reference UNIQUE, created_at)`를 만든다. `item`은 `lotto_ticket`, `speetto_ticket`이다. 수량은 합계로 계산한다.
- 상점, 로또, 스피또 화면에 보유 이용권 수를 보여 준다. 이용권이 있으면 골드 대신 이용권으로 살 수 있다(버튼에서 선택).

### 3-2. 예굼쿠지
- **판 구성**: 100장. 등급별 장수는 A 1 · B 2 · C 3 · D 6 · E 10 · F 15 · G 25 · H 38(지금 화면과 같음). 판은 모든 플레이어가 함께 쓴다. 칸의 등급 배치는 서버가 판을 만들 때 `crypto` 난수로 섞는다. 산 칸의 등급만 공개한다.
- **가격**: 지금 값을 유지한다. 1장 300G, 그날 본인 기준 6번째 장부터 400G.
- **보상**
  | 등급 | 보상 |
  | --- | --- |
  | A | 10점 + 100G |
  | B | 5점 + 50G |
  | C | 3점 + 30G |
  | D | 1점 + 10G |
  | E | 무료 로또 이용권 3장 |
  | F | 무료 로또 이용권 1장 |
  | G | 스피또 이용권 3장 |
  | H | 스피또 이용권 1장 |
  | 라스트원 | 판의 **마지막 1장**을 산 사람에게 그 칸 보상과 별도로 1,000G |
- 여러 칸을 한 번에 살 수 있다. 고른 칸 중 하나라도 이미 팔렸거나 골드가 모자라면 **전부 실패**한다(부분 구매 없음). 동시에 같은 칸을 사려 하면 한 사람만 성공한다.
- 마지막 장이 팔리면 다음 요청에서 새 판을 만든다. 판 번호를 보여 준다.
- **화면 변경**
  - "남은 칸" 문구를 **"남은 쿠지"**로 바꾼다.
  - 쿠지판 하단의 등급 목록(A~H)에 **라스트원**을 추가한다.
  - 등급(또는 라스트원)을 누르면 **모달**로 그 등급의 보상과 남은 장수를 보여 준다. 모달은 기존 시트(`.kuji-sheet`) 스타일을 따르고, 닫기 버튼·바깥 누르기·Esc로 닫힌다.

### 3-3. 데일리 로또
- 이름을 "로또"에서 **"데일리 로또"**로 바꾼다(상점, 화면 제목, 내역 문구 모두).
- 1장에 1~25 중 서로 다른 숫자 5개를 고른다. 가격은 지금 값(500G) 또는 무료 로또 이용권 1장이다.
- **추첨**: 매일 17:00(KST). 1~25 중 서로 다른 5개를 서버가 `crypto` 난수로 뽑는다. 17:00 이후 첫 요청에서 그날 추첨 결과를 한 번만 만든다(`lotto_draws(date PK)`). 17:00 전에 산 표는 그날 추첨, 17:00 이후에 산 표는 다음 날 추첨 대상이다.
- **당첨금**: 5개 일치 1등 5,000G · 4개 2등 3,000G · 3개 3등 1,000G · 2개 4등 500G · 그 밖 낙첨. 지급은 추첨 후 멱등 정산한다.
- 하루 구매 수 제한은 두지 않는다.
- 결과 화면에 내 표별 일치 개수와 당첨금을 보여 준다.

### 3-4. 스피또
- 가격은 지금 값(300G) 또는 스피또 이용권 1장이다.
- 당첨 확률 **10%**, 당첨금 **1,500G**. 당락은 **구매 순간 서버가 `crypto` 난수로 정한다**. 칸에 놓일 캐릭터 배치도 서버가 만든다. 당첨이면 같은 캐릭터 3개가 있고, 낙첨이면 어떤 캐릭터도 3개가 되지 않게 배치한다. 칸 수와 레이아웃은 지금 화면을 따른다.
- 긁기 연출은 클라이언트에서 하지만, 결과와 지급은 구매 응답에서 이미 확정돼 있다. 긁다가 화면을 나가도 지급은 유지된다.

### 3-5. 테스트 (필수)
- 쿠지: 가격 증가 경계(5번째·6번째), 다중 구매 전부 실패, 동시 구매, 라스트원 지급, 새 판 생성, 등급별 보상과 이용권 지급
- 로또: 17:00 경계의 대상 회차, 추첨 1회만 생성, 당첨 등수 판정, 이용권 사용
- 스피또: 확률은 난수 함수를 주입해서 테스트, 낙첨 배치에 3개 일치가 없는지, 이용권 사용
- 공통: 잔액 부족, requestId 중복, 운영자 403

## Phase 4 — 캐치마인드 (그리기 도구, 컬러 피커, 서버)

### 4-1. 규칙 (기존 yegoom 스캐치마인드 방식)
- 날짜 구분 없이 **한 판씩 이어진다**.
- **그릴 차례**는 한 사람이 가진다. 아무도 없으면 플레이어 누구나 먼저 맡을 수 있다.
- **제시어**: 차례를 가진 사람에게만 무작위로 보인다. 마음에 안 들면 3번까지 바꿀 수 있다. 제시어 목록은 `iam-yeseo/yegoom`의 `src/lib/skatch-mind-words.js`(400개)를 가져와 `shared/`에 둔다. 접근할 수 없으면 멈추고 보고한다.
- **출제**: 그림을 확정하면 판이 열린다. 낸 그림은 바꿀 수 없다.
- **맞히기**: 출제자를 뺀 플레이어 누구나 답을 말할 수 있다. 말한 답은 모두에게 보인다. 공백은 무시하고 비교한다.
- **힌트·종료**(지금 화면 규칙 유지): 오답이 3개가 되면 첫 글자와 글자 수 힌트가 열린다. 오답이 6개가 되면 판이 끝난다.
- **보상**: 가장 먼저 맞힌 사람이 **3점 + 5G**를 받고 판이 끝난다. 힌트 후에도 같다(기존 50/30점 임시값 폐기). 그 사람이 다음 차례가 된다.
- 아무도 못 맞히고 6번째 오답으로 끝나면 보상은 없고 차례는 출제자에게 남는다. 출제자는 판을 직접 끝낼 수도 있다(차례 유지).
- 출제자 감점 규칙은 이번에 넣지 않는다.
- 화면이 열려 있는 동안 5초 간격으로 판 상태를 새로 고친다. 화면이 숨겨지면 멈춘다.
- 그림 저장: 정사각형 캔버스를 PNG(또는 WebP) data URL로 저장한다. 300KB를 넘으면 서버에서 거절한다. 테이블 구조는 자유이고, 판·답·차례를 분리한다.

### 4-2. 그리는 화면
- 도구를 **아이콘 버튼**으로 바꾼다. 펜, 지우개, 채우기(영역 채우기) 3종이다. 텍스트 버튼은 쓰지 않는다. 아이콘은 프로젝트에 새 의존성 없이 인라인 SVG로 만든다(앱의 기존 선 굵기·둥근 끝 스타일). 각 버튼에 `aria-label`과 선택 상태(`aria-pressed`)를 단다.
- **채우기**: 탭한 지점과 같은 색 영역을 현재 색으로 채운다(스캔라인 flood fill). 안티앨리어싱 경계에서 틈이 생기지 않게 허용 오차를 둔다.
- 굵기 3단계는 지금처럼 유지한다.
- 실행 취소 1단계 이상을 지원한다.

### 4-3. 컬러 피커
사용자가 준 shadcn `color-picker.tsx`의 **구성과 동작을 따르되, 이 레포 구조에 맞게 옮긴다.**
- 이 레포는 Tailwind·shadcn을 쓰지 않는다. **Tailwind, shadcn, Radix, `color`, `lucide-react`를 설치하지 않는다.** Tailwind의 기본 리셋이 기존 디자인 CSS를 깨뜨리기 때문이다. `src/components/ColorPicker.tsx`에 의존성 없는 React 컴포넌트와 기존 CSS 파일 스타일로 구현한다.
- 포함할 것
  - 채도·명도 선택 영역(원본의 `ColorPickerSelection`): **가로는 채도, 세로는 명도**로 둘 다 반영한다. 원본은 세로 값으로 채도만 바꾸는 버그가 있으니 고친다.
  - 색상 슬라이더(원본의 `ColorPickerHue`)
  - 투명도 슬라이더(원본의 `ColorPickerAlpha`). 펜에만 적용하고, 채우기는 불투명으로 처리해도 된다(판단 후 보고).
  - HEX 표시와 입력(원본의 `ColorPickerFormat` HEX 모드만)
  - 자주 쓰는 색 견본(지금 화면의 색) + 최근 사용한 색 5개
- 빼는 것과 이유
  - 스포이드(EyeDropper): iOS Safari와 Android Chrome에서 지원하지 않음
  - 출력 형식 선택(RGB, CSS, HSL): 그리기에 필요 없음
- 원본의 다른 버그도 고친다. 제어 값이 바뀔 때 r·g·b를 h·s·l 자리에 넣는 문제, `pointerup` 리스너가 해제되지 않는 문제다.
- 피커는 그리기 화면에서 색 버튼을 누르면 아래에서 올라오는 시트로 연다. 포인터·터치 드래그(`touch-action: none`)와 키보드 조작(화살표)을 지원한다.
- 터치 이펙트(Phase 5)가 피커와 캔버스 위에서는 나오지 않게 `data-notouchfx`를 붙인다.

### 4-4. 테스트 (필수)
- 차례 맡기, 제시어 변경 3회 제한, 출제자 답 금지, 정답 판정(공백 무시), 동시 정답 시 한 명만 보상, 힌트 3·종료 6, 차례 이동, 이미지 크기 제한
- 컬러 피커: HSV↔HEX 변환 왕복, 드래그 위치 → 색 계산 단위 테스트

## Phase 5 — 전역 터치 이펙트

- 화면 아무 곳이나 누르면, 누른 지점에 작은 이펙트를 보여 준다. 부드러운 원이 퍼지며 사라지고, 앱 팔레트 색 점 3~4개가 튄다. 400ms 이하다.
- `src/motion.ts`에 `installTouchEffect()`를 만들고, `installPressFeedback()`과 같은 곳에서 한 번 설치한다. 기존 `fxLayer()`를 쓴다.
- 규칙
  - transform·opacity만 움직인다.
  - `prefers-reduced-motion`이면 아무것도 하지 않는다.
  - 주 포인터의 `pointerdown`에만 반응한다. 마우스는 왼쪽 버튼만이다.
  - 스크롤·드래그를 방해하지 않는다(`passive` 리스너, `preventDefault` 금지).
  - 60ms 안에 다시 누른 것은 무시하고, 화면에 동시에 남는 이펙트는 최대 8개다.
  - 다음 위에서는 나오지 않는다: `input`, `textarea`, `select`, `canvas`, `[contenteditable]`, `[data-notouchfx]`와 그 안쪽
  - 기존 버튼 눌림 피드백(`installPressFeedback`)과 겹쳐도 어색하지 않게, 이펙트 크기는 작게(지름 최대 44px) 한다.
- 테스트: reduced motion에서 노드가 생기지 않는지, 제외 요소에서 생기지 않는지, 노드가 400ms 뒤 제거되는지(e2e)
