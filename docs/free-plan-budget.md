## 개선 PR 7 — 슬롯머신

기준 main `9fc547c`에서 PR 2의 인증 포함 D1 측정 래퍼를 재사용했다. [PR 7 원자료](free-plan-pr7-measurements.json)에 실제 로컬 D1/workerd **60개 표본**을 남겼다. 오전 KST 09시, 최근 기록 3개/같은 날 5,000개, 표시 기간 밖 기록 0/5,000개, 과거 골드 원장 0/10,000행, 낙첨/당첨 및 동일 요청 재시도를 비교한다. 운영 DB·API에는 접근하지 않았다.

아래 값은 **SQL 문장 / rows_read / rows_written**이며 인증·기존 로또 정산 확인·잔액 조회·캐시 트리거·인덱스 갱신까지 포함한다. 과거 슬롯 5,000개와 골드 원장 10,000행이 있는 표본이다. 최근 기록 3개 열의 조회는 스핀 전 3개, POST 응답·재요청에는 새 기록을 포함한 4개를 반환한다. 최근 같은 날 5,000개 열은 항상 최대 20개만 반환한다.

| 요청 | 최근 3개 | 최근 같은 날 5,000개 |
| --- | ---: | ---: |
| GET 슬롯 | 4 / 10 / 0 | 4 / 26 / 0 |
| POST 낙첨 | 8 / 17 / 10 | 8 / 32 / 10 |
| POST 당첨 | 9 / 20 / 16 | 9 / 35 / 16 |
| POST 같은 요청 재확인 | 5 / 12 / 0 | 5 / 27 / 0 |
| bootstrap — 스핀 전/후 동일 | 15 / 74 / 0 | 15 / 74 / 0 |

스핀 한 번의 논리 기록은 **낙첨 2행**(영수증·차감 원장), **당첨 3행**(상금 원장 추가)이다. D1의 실제 쓰기 집계는 캐시·인덱스 갱신을 포함해 **10행/16행**이었다. 재확인은 쓰기 0이며 낙첨 batch는 2문장, 당첨 batch는 3문장이고 둘 다 전체 요청 binding 호출은 7회다. SQL 문장과 `db.batch()` 호출 수를 혼동하지 않는다.

표시 기간 밖 기록을 0→5,000개로 늘린 표본의 슬롯 요청 읽기는 요청당 1행 차이로 제한됐고, 골드 원장 10,000행 추가는 슬롯 조회·스핀 비용을 늘리지 않았다. 사용자/날짜 접두 인덱스에 정렬 키 `created_at DESC, id DESC`를 함께 넣었고, `EXPLAIN QUERY PLAN`의 임시 B-tree 정렬이 없는지 회귀 검사한다. 같은 날짜·같은 시각에 5,000개가 쌓인 표본에서도 조회 26행으로 제한됐다. 최근 반환 목록이 3→20개로 커지는 비용은 표에서 별도로 비교한다.

bootstrap에 슬롯 조회·집계를 추가하지 않았다. 큰 원장 표본은 스핀 전후 15문장/74행으로 같았고 작은 원장은 새 차감·당첨 원장 행이 기존 최근 원장 목록에 보이는 만큼만 읽기량이 늘었다. 기존 화면별 30초/60초 폴링·숨김 중단 정책은 유지하며 슬롯 전용 폴링은 없다. 오후의 기존 로또 안내·정산 비용은 PR 6과 같다.

예를 들어 4명×20스핀은 80회다. 위 큰 기록 표본과 7% 당첨 기대값으로, 스핀당 POST·기존 후속 bootstrap 각 1회, 사용자당 최초 슬롯 조회 1회를 더하면 **164요청·약 1,862문장·약 8,601행 읽기·약 834행 쓰기**다. 계산은 POST `80×(0.93×8+0.07×9)`, 읽기 `80×(0.93×32+0.07×35)+80×74+4×26`, 쓰기 `80×(0.93×10+0.07×16)`이다. 실제 당첨 횟수·추가 화면 이동·폴링·재확인·다른 게임 요청은 별도다. 일일 플레이 제한이 없으므로 이 수치는 사용량 제한이 아니라 해당 가정의 예산이다.

PR 7 검증: `npm run check` **19파일/756개**(D1 통합 **304개**, 신규 12개)·타입·빌드 통과. 이후 슬롯의 과거 당첨 영수증 확인 시 잔액 표시를 보완하고 타입·빌드와 해당 브라우저 검사도 다시 통과했다. 최종 전체 Playwright는 신규 슬롯 9개를 포함해 **113개 통과(7.8분)**, 배포 dry-run도 통과했다. 첫 전체 실행은 기존 인형뽑기 첫 canvas 그리기가 기준 100ms를 넘은 136ms로 111개 통과·1개 실패였다. 같은 빌드의 단독 실행은 93.3ms였으며 짧은 타입 검사와 겹쳤을 가능성도 기록했다. 최종 전체 실행에서는 90.9ms였고 인형뽑기 코드·측정 도구·기준은 바꾸지 않았다. 원인을 단정하지 않고 세 원자료를 [검증 기록](pr7-validation.json)에 보존한다. 원격 마이그레이션·머지·실제 배포는 하지 않았다.

## 개선 PR 6 — 데일리 로또·스피또

기준 main `f8ca8c1`과 같은 인증 포함 D1 래퍼·fixture를 비교했다. [PR 6 요청 원자료](free-plan-pr6-measurements.json)는 오전/오후×과거 표0/5,000장(종류별)의 bootstrap·로또·스피또 **12개 표본** 및 기존 큰 원장 bootstrap **12개 전후 표본**을 담는다. 로컬 D1/workerd 측정이며 운영 DB에 접근하지 않았다.

아래는 **SQL 문장 수 / rows_read**다. 과거 표는 이미 정산된 2026년01월01일 표이며 각 종류에 최근3장이 따로 있다. 구매·지급·동시 요청은 별도 규칙 테스트로 확인한다. 조회 표본의 rows_written은 전후 모두0이다.

| 시각·조회 | 과거0장: 이전 → 이후 | 과거5,000장/종류: 이전 → 이후 |
| --- | ---: | ---: |
| 09시 bootstrap | 15 / 25 → 15 / 23 | 15 / 5,025 → 15 / 23 |
| 09시 로또 | 4 / 22 → 4 / 20 | 4 / 30,022 → 4 / 20 |
| 09시 스피또 | 4 / 16 → 4 / 14 | 4 / 20,016 → 4 / 14 |
| 18시 bootstrap | 15 / 26 → 16 / 26 | 15 / 5,026 → 16 / 26 |
| 18시 로또 | 5 / 24 → 5 / 22 | 5 / 30,024 → 5 / 22 |
| 18시 스피또 | 4 / 17 → 4 / 15 | 4 / 20,017 → 4 / 15 |

최근7일 필터는 기존 `shop_user_date_idx(user_id,date,kind)`로 오래된 구매를 제외한다. 함께 측정한 기존 미정산 후보 조회가 전체 추첨일 인덱스를 고르면 정산 완료 표도 읽는 것이 확인돼, 동일한 `settled_at IS NULL` 조건에 이미 있는0011의 `lotto_tickets_due_idx` 부분 인덱스를 명시했다. 스키마·정산 대상·지급 규칙은 바꾸지 않는다. 이 두 조치 뒤 과거0장과5,000장의 개선 후 비용이 같아졌다. 오늘/최근7일에 산 표 자체가 늘면 읽기량도 늘 수 있다.

`lottoNotice`는17시30분 전 null을 추가 쿼리 없이 반환하고, 이후에는 COUNT/SUM 집계 **1문장**을 추가한다. 위 fixture의 오후 안내는2행을 읽지만 기존 정산 확인에서2행을 줄여 총 rows_read는 과거0장 표본에서도 그대로다. 이 안내는 정산된 오늘 표도 세므로 기존 full `(draw_date,settled_at)` 인덱스를 사용한다. 사용자별 오늘 표의 실제 수에 따라 비용이 달라진다. 닫기/확인 기억은 localStorage이며 서버 요청을 추가하지 않는다.

큰 골드/이용권 원장(각100/10,000행) fixture의 오전 bootstrap12개 중 해당6개는 쿼리·읽기 비용이 동일하다. 오후6개는 prepare/문장/binding 호출만 **+1**, rows_read는 동일하다. 10,000행 기준 오전 idle15/161·open17/164, 오후 idle15/162→16/162·open17/165→18/165다. 기존 회귀 테스트도 이 오후1쿼리만 허용하고 행 읽기 상한은 유지한다.

홈·랭킹30초/기타화면60초·숨김/뽑기/미리보기 중단 정책은 그대로다. 4명×10시간×30초를 보수적으로 모두 오후 최대 표본(18문장/165행)에 대입하면 **4,800요청·86,400문장·792,000행/일**이다. 이전 같은 큰 원장 표본은81,600문장·792,000행이었으므로 요청·읽기량은 같고 문장만 최대4,800개 늘어난다. 실제17시30분 전에는 안내 쿼리가 없고, 추첨 시각·지급·새 점수·오늘 표·복귀·여러 탭·상점 진입/구매는 실제 표본 비용으로 따로 더한다.

오늘 표가 없는 같은 큰 원장 fixture의 오후 비용을 이전 화면별 예산에 대입하면, PR4 캐치마인드 공개 화면(4명·10시간)은 bootstrap2,400회에 각1문장이 더해져98,400→100,800문장/일이며 요청31,200건·읽기511,200행은 같다. PR5의4명×20플레이 예시도 bootstrap80회만 늘어2,700→2,780문장/일이며 요청260건·읽기14,960행은 같다. 오늘 표가 있거나 실제 정산이 발생하면 그 표본의 행 읽기를 사용한다.

명시적인7일 밖 lotto requestId 재시도는 최근목록과 별도로 본인 영수증1장을 읽어 원래 결과를 돌려준다. 이 드문 복구 경로에만1쿼리가 추가되며 history에 오래된 행을 끼워 넣거나 다시 차감하지 않는다. 과거 미정산 표의 정산과 원장 보존은7일 표시 제한과 별개다.

PR 6 최종 검증: `npm run check` **17파일/734개**(D1 통합 **292개**)·타입·빌드 통과. 마지막 자정 지연 응답 보완 뒤 관련11개·타입·빌드도 다시 통과했다. 전체 Playwright는 신규6개를 포함해 **103개 통과**했다. 첫 전체 실행은 기존 그리기 성능 검사에서99ms Long Task 1건을 관측해102개 통과·1개 실패였다. 소스·빌드·측정 기준을 바꾸지 않은 단독 및 전체 재실행에서는 해당 검사가 통과했다. 원인을 단정하지 않으며 세 표본을 [검증 원자료](pr6-validation.json)에 모두 보존한다. 배포 dry-run과 문서 링크·이미지 확인을 마쳤고 실제 배포는 하지 않았다.

PR #28 기록 머리글 보완 후 `npm run check` **17파일/734개**·타입·빌드와 관련 `shop-pr6.spec.ts` Playwright **7개**가 통과했다. 미공개 스피또 당첨 제외, 낙첨 공개 후 금액 숨김, 같은 날짜 당첨을 차례로 공개할 때의 합산, 재선택 시 중복 합산 방지, 로또 추첨 대기·낙첨 그룹의 금액 숨김을 확인했다. 스피또 기록 390px·560px 캡처를 갱신했다. 이 보완에서는 전체 Playwright를 재실행하지 않았다.

## 개선 PR 5 — 캐릭터 뽑기

기준 main `2f20512`와 같은 인증 포함 D1 래퍼·고정 기계·강집게 fixture를 실제 로컬 D1에서 비교했다. [PR 5 요청 원자료](free-plan-pr5-measurements.json)의 **8개 표본은 prepare·실행 SQL·binding 호출·rows_read·rows_written 모두 동일**하다. 뽑기 판정·보상·DB·API는 수정하지 않는다. 표는 **SQL 문장 / rows_read**이며 batch 안의 문장도 각각 센다.

| 요청 | 이전 main → PR 5 | rows_written |
| --- | ---: | ---: |
| bootstrap, 기계 진입 전 | 15 / 23 → 15 / 23 | 0 |
| GET 기계, 최초 생성 | 7 / 8 → 7 / 8 | 3 |
| GET 기계, 저장된 판 | 3 / 4 → 3 / 4 | 0 |
| bootstrap, 기계 생성 후 | 15 / 24 → 15 / 24 | 0 |
| POST 플레이, 인형 보상 있음 | 13 / 17 → 13 / 17 | 17 |
| 같은 플레이 재요청 | 4 / 5 → 4 / 5 | 0 |
| GET 기계, 플레이 후 | 3 / 4 → 3 / 4 | 0 |
| bootstrap, 보상 후 | 15 / 29 → 15 / 29 | 0 |

보상 플레이의 D1 binding 호출은 10회이며 원자료에 문장 수와 구분해 기록했다. 반환한 최종 인형 위치·상품·원장도 같은 엔진 결과와 비교한다. 기존 큰 원장의 bootstrap 12개 회귀 표본도 유지한다. 위 비용은 빈 과거 원장 부근의 고정 fixture이며 클리어·충전·과거 점수·미정산 게임에 따른 운영 비용의 상한은 아니다.

뽑기 화면의 bootstrap/기계 주기 폴링은 계속 **0회**다. 3~4명이 하루 10시간 화면을 열어 두어도 정지 상태의 반복 API 요청은 없다. 화면 진입·복귀·충전 경계·구매·플레이와 결과 확인 후 읽기만 발생한다. 충전·쿨다운 글자는 기기 안에서 갱신하므로 서버 요청을 추가하지 않는다. 플레이 후 bootstrap 1회는 계속 보내되 재생이 그 응답을 기다리지 않으며, 코인 구매는 기존 잔액 확인 흐름을 유지한다.

예를 들어 4명, 각 20플레이/일, 플레이마다 POST·bootstrap·결과 확인 후 GET 각 1회, 그 밖의 진입/복귀/충전 GET을 각 5회로 가정하면 **260요청/일**이다. 작은 fixture 비용을 그대로 대입하면 2,540문장·4,080행이며, bootstrap만 기존 큰 fixture의 17문장·165행으로 바꾸면 **2,700문장·14,960행/일**이다. 새 계정 초기화·추가 재시도·코인 구매·당주 점수 증가·다른 게임·다중 탭은 별도다. 이 예시는 실측 표본을 이용한 계산이며 운영의 확정 사용량이나 상한을 뜻하지 않는다.

새 재생 Worker와 캐시 캔버스는 기기 안에서만 일한다. Worker 스크립트는 기존 정적 자산 사전 캐시에 포함되며 API나 D1을 호출하지 않는다. UI 성능 전후와 재현 조건은 [브라우저 원자료](free-plan-pr5-performance.json)에 기록한다.

## 개선 PR 4 — 캐치마인드

### 하루 10시간, 3~4명 폴링

상태가 변하지 않는 구간의 계산이다. `since`가 같은 GET은 인증 포함 2문장·최대 4행, bootstrap은 기존 큰 fixture의 17문장·165행을 사용했다. 시작·화면 복귀·사진·게임 변경 요청과 그에 따른 bootstrap은 다음 문단처럼 별도로 더한다.

| --- | --- | ---: | ---: | ---: | ---: |
| 캐치마인드 화면 bootstrap | 60초 | 1,800 | 2,400 | 40,800 | 396,000 |

공개 판의 이전 PR 3 예상은 597,600행/일이었다. 이제 같은 가정은 511,200행(읽기 한도의 약 10.22%)이며 Worker 요청 수는 open의 5초 주기를 유지하므로 같다. 대기·종료는 GET 주기가 5→10초로 늘어 서버 요청도 줄어든다. 자기 초안은 주기 GET이 없지만 가시성·온라인 복귀 때 인증 상태를 확인한다.

실제 게임이 변할 때는 전체 응답과 저장 후 갱신을 더한다. 예를 들어 20판/일, 판당 시작 1·공개 1·바꾸기 3·오답 10이면 변경 요청 300건이다. 변경마다 다른 3명이 한 번씩 관측한다고 넉넉히 잡으면 기존 GET 중 최대 900건을 전체 응답으로 바꾸고, 본인/동료의 bootstrap 갱신을 최대 1,200건 더한다. 전체 응답과 변경의 기본 행 읽기를 각각 100행, 단어 선택 80회의 추가 스캔을 각각 400행으로 **가정**하면 약 857,600행/32,700요청/일이다. 이 100행은 측정 상한이나 코드 보장이 아니며, 실제 답변·사진·점수 데이터에 맞춰 원자료와 운영 지표로 다시 계산한다.

계산식은 `bootstrap 수 × 실제 bootstrap 행 + unchanged 수 × 4 + 전체 GET 행의 합 + 변경 요청 행의 합`이다. 전체 GET은 unchanged와 중복해서 세지 않는다. 여러 탭·기기·다른 게임은 추가 예산을 사용하며, 쓰기는 D1의 트리거·인덱스 갱신까지 포함한 실제 rows_written으로 확인한다.

## 정산·쓰기 비용

- 예측 정산은 할 일이 없을 때 1 SELECT, 밀린 판이 있을 때 판·규칙 조회 → 해당 예측 조회 → 지급/완료 batch로 **최대 3 binding 호출**이다. 30일치 판 30개를 한 요청에서 모두 정산하고 각 골드·점수 30행을 지급하는 회귀 검사가 있다. 인증 포함 실제 bootstrap 전체는 **17 binding 호출·106 SQL 문장·371 rows_read·361 rows_written**이다. SQL 문장은 50개를 넘지만 HTTP 전체 binding 호출은 50 이하다. 반복 조회는 지급을 만들지 않는다.
- 로또는 추첨이 이미 있고 정산할 표가 없으면 오전·오후 모두 1 SELECT다. 누락 추첨 생성 batch와 모든 해당 표 조회, 지급·알림·정산 batch를 합해 **최대 4 binding 호출**이다. 같은 날짜의 동시 추첨은 저장된 당첨 번호를 사용한다. 과거 정산을 일부만 처리하거나 미지급 잔액을 반환하지 않는다.
- 실제 정산의 rows_read/rows_written와 CPU는 지급할 판·표 수에 비례한다. 장기간 미접속 뒤의 대량 정산은 단순 폴링 예산과 다르며, 아래 일일 표에는 포함하지 않는다. batch로 호출 한도를 낮췄지만 무제한 크기의 batch나 운영 CPU 충족을 보장하지 않는다.
- 골드 또는 이용권 원장 INSERT마다 파생 잔액 INSERT/UPDATE가 한 번 추가된다. D1 쓰기 비용에는 인덱스 갱신도 포함되므로 논리적 지급 수를 rows_written와 동일시하지 않는다. 중복 reference로 무시된 INSERT와 실패 batch는 캐시를 바꾸지 않는다. 기존 동시 구매·재시도·실패 테스트에서도 두 원장 합계와 캐시를 비교한다.
- Cron은 하루 한 번 3개 DELETE를 한 batch로 실행하며 테이블별 최대 500개를 삭제한다. 논리 삭제 최대 1,500행에 인덱스 비용이 더해진다. 남은 만료 기록은 다음 날 처리한다. 살아 있는 제한 버킷·세션, 원장·그림·답변은 보존한다. guess 영수증은 FK 때문에 지우지 않고, 현재/진행 중 판의 영수증도 보존한다.
- 성공 로그인은 자기 버킷/이전 세션만 정리한다. 한도+1에 도달한 버킷은 계속 요청해도 추가 쓰기가 없고 만료 뒤 재시작한다. 두 로그인 버킷 중 하나가 아직 한도에 이르지 않았으면 그 버킷에는 계속 제한 기록을 남긴다.

## 3~4명, 하루 10시간의 폴링 예산

브라우저 탭 하나가 계속 보이고 온라인인 경우다. 시작·화면 진입·저장·탭 복귀·인증·사진 요청은 별도이며, 모두 같은 한도를 사용한다. 정산 없는 가장 큰 fixture 값인 bootstrap 17문장/165행을 사용한 **예상값**이며 4명 DB 자체를 실측한 값은 아니다.

홈과 캐치마인드의 하루 합계를 중복해 더하지 않는다. 한 탭은 한 화면을 표시한다. 홈 고정은 무료 읽기의 15.84%, 캐치마인드 고정은 11.95%, 후자는 Worker 요청의 31.2%다. 변경 전에는 모든 일반 화면 bootstrap이 30초여서 같은 4명·10시간 홈의 큰 원장 fixture는 32,889,600행/일(한도의 약 6.58배), 캐치마인드는 bootstrap 포함 33,091,200행/일이었다.

BroadcastChannel 리더 선출은 이번에 넣지 않았으므로 표시 중인 탭 수만큼 예산을 곱해야 한다. 운영 대시보드에서 다른 Worker/D1 사용량과 합산해 확인한다.

## CPU와 번들

30회 로컬 Node process CPU(user+system) 측정이다. PNG/WebP는 실제 validator에 들어가는 300KiB 경계 fixture이며 base64 검증·디코딩·컨테이너 검사를 모두 포함한다. 실제 이미지 픽셀 디코딩 비용 측정은 아니다.

| 대상 | 변경 전 중앙값 / p95 | 변경 후 중앙값 / p95 |
| --- | ---: | ---: |
| PNG 검증 | 29.227 / 80.466ms | 2.167 / 4.762ms |
| WebP 검증 | 19.554 / 73.858ms | 1.372 / 1.809ms |
| CRC 단독 | 9.467 / 10.181ms | 0.683 / 0.759ms |
| 로그인 KDF 확인, 변경 없음 | 13.600 / 16.439ms | 동일 구현 |
| 비밀번호 확인+교체, 변경 없음 | 27.327 / 31.423ms | 동일 구현 |

CRC 표만으로는 PNG 중앙값 20.517ms였으므로, `atob` 결과를 `Uint8Array.from` callback 대신 직접 복사해 추가 비용을 줄였다. 손상 CRC·잘못된 형식·치수·상한 검사는 유지한다. 비밀번호 강도를 낮추지 않았다. 로컬 비밀번호 CPU가 10ms를 넘으므로 **운영 무료 CPU 한도 충족은 미확인**이다. 운영 observability에서 실제 CPU p95와 exceededCpu 여부를 확인해야 하며, 이 PR은 배포나 실 API 호출로 확인하지 않는다.

main JS는 기존 약 504kB에서 **437.06kB, gzip 140.92kB**로 줄었다. 운영·주식·뽑기·물리 엔진은 별도 chunk다. 서비스 워커는 오프라인 미리보기의 정적 파일을 계속 사전 캐시하므로 이 수치는 초기 평가 대상 감소이며 최초 설치 전체 다운로드 감소를 뜻하지 않는다.

## 저장 공간 전망

캐치마인드는 디코딩된 이미지 최대 300KiB를 base64 TEXT로 저장하므로 한 그림은 최대 약 **400KiB**다. 프로필 최대 260KiB BLOB은 사용자당 한 장이고 교체된다. 행운 사진은 날짜당 최대 440KiB BLOB이다. 원장·정산·답변과 인덱스 공간은 별도로 계속 증가한다. 정리 Cron은 그림을 삭제하지 않는다.

| 최댓값 가정 | 사진 본문 증가량 | 500MB 도달 단순 예상 |
| --- | ---: | ---: |
| 그림 5판/일 + 행운 사진 1장/일 | 약 2.50MB/일 | 약 200일 |
| 그림 10판/일 + 행운 사진 1장/일 | 약 4.55MB/일 | 약 110일 |
| 그림 20판/일 + 행운 사진 1장/일 | 약 8.64MB/일 | 약 58일 |

십진 MB로 계산한 본문만의 상한 시나리오이며 프로필 4장 약 1.06MB, 기존 데이터·페이지·인덱스·신규 주식 데이터 때문에 실제 여유 기간은 짧아진다. 실제 압축된 그림이 작으면 늘어난다. DB 크기 70% 지점부터 증가 속도를 확인하고 후속 저장 방식/보존 정책을 결정해야 한다. 이 PR에서 영구 그림·점수·골드 내역을 임의로 삭제하거나 외부 스토리지로 옮기지 않는다.
