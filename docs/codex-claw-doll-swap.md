# 작업 지침: 캐릭터 뽑기 인형 그림 교체 (Codex용)

## 0. 한 줄 요약

캐릭터 뽑기(인형뽑기 기계)에 들어 있는 **인형 그림 11종을 사용자가 준 새 인형 그림 15종으로 바꾼다.**
게임 규칙·물리 계산·보상·화면 구성·DB는 그대로 둔다. **바뀌는 것은 "기계 안에 보이는 인형 그림"과 "인형 종류 수(11 → 15)" 둘뿐이다.**

- 원본 이미지는 **15장**이고 **배경이 있다**(투명 PNG가 아님). 배경 지우기가 이 작업의 큰 부분이다.
- 받은 장수가 15장이 아니면 시작하지 말고 사용자에게 묻는다.

---

## 1. 절대 하지 말 것

아래 중 하나라도 필요해 보이면 **멈추고 사용자에게 물어본다.** 임의로 진행하지 않는다.

1. **그림을 새로 그리거나 생성하거나 고쳐 그리지 않는다.** 색 보정·필터·외곽선 추가·AI 업스케일도 쓰지 않는다. 할 일은 배경 지우기, 여백 자르기, 크기 줄이기, WebP 변환뿐이다.
2. **물리 엔진 계산을 건드리지 않는다.** `shared/claw-physics.ts`에서 바꿀 것은 3-3절의 상수 3개(`DOLL_TYPES`, `DOLL_WEIGHT`, `DOLL_RADIUS`)와 주석 한 줄뿐이다. `MACHINE`, `CLAW`, `DOLL_COUNT`(30), `MAX_RADIUS`, `createBoard`·`simulateAttempt`·`stepBoard` 등 함수 본문은 그대로 둔다.
3. **`tests/fixtures/gatcha-physics.original.js`는 한 글자도 바꾸지 않는다.** 이 파일의 Git blob SHA를 검사하는 테스트가 있다. 원본 엔진과의 대조 기준이다.
4. **DB를 건드리지 않는다.** 새 마이그레이션을 만들지 않고, 사용자들의 기계(`claw_accounts.board_json`)를 비우거나 다시 만들지 않는다. 원격 DB 명령(`--remote`), 배포(`npm run deploy`), `launch:reset` 같은 스크립트는 실행하지 않는다.
5. **보상·확률·코인·도전과제·운영 설정을 바꾸지 않는다.** `shared/balance.ts`의 `CLAW_RULES`, `worker/claw.ts`, `shared/achievements.ts`, 운영 탭(`src/screens/Admin.tsx`)은 손대지 않는다.
6. **기계 화면을 바꾸지 않는다.** `src/claw/render.ts`, `src/screens/Claw.tsx`, `src/claw/sound.ts`, `src/claw/controller.ts`는 수정하지 않는다. 렌더러는 `DOLL_TYPES` 수만큼 그림을 자동으로 불러오므로 고칠 필요가 없다. 안내 문구의 "11종"도 `{DOLL_TYPES}종`이라 자동으로 "15종"이 된다.
7. 인형에 이름·등급·희귀도 같은 **새 기능을 추가하지 않는다.** 지금 게임에는 인형 이름이 없다. 그대로 둔다.
8. **원본 이미지(큰 PNG)를 `public/` 아래나 저장소에 넣지 않는다.** `public/` 아래 파일은 전부 서비스 워커가 미리 받아 두므로, 큰 원본이 들어가면 모든 사용자가 몇 MB를 받게 된다. 원본은 저장소 밖 임시 폴더에 두고 커밋하지 않는다.
9. 4절 목록에 없는 파일을 "김에 정리"하지 않는다. 리팩터링·포맷 변경·의존성 업데이트 금지.

## 2. 지금 구조 (꼭 알아야 할 것)

### 2-1. 인형 번호(type)와 그림 파일

- 인형마다 `type` 번호(1부터)가 있고, 그림 파일은 `public/claw/dolls/doll-{type}.webp`다. 지금은 `doll-1.webp` ~ `doll-11.webp`. 바꾼 뒤에는 `doll-1.webp` ~ `doll-15.webp`.
- 경로는 `src/claw/render.ts`의 `dollSrc(type)`가 만들고, 결과 창(`src/screens/Claw.tsx`)도 같은 함수를 쓴다. 파일 이름 규칙을 그대로 지키면 코드는 고칠 필요가 없다.
- 지금 그림들은 **투명 여백 없이 인형 테두리에 딱 맞게 잘려 있다**(알파 bbox = 이미지 전체). 긴 변은 320px이다.
- 렌더러는 인형을 **긴 변이 `radius × 2.3`이 되게** 그린다(`drawDoll`). 그래서 새 그림도 **투명 여백을 완전히 잘라내야** 인형이 지금과 같은 크기로 보인다. 여백이 남으면 인형이 작아 보이고 집게가 허공을 잡는 것처럼 보인다.
- 그림을 못 불러오면 🧸 이모지로 대신 그린다. 화면에 🧸가 보이면 그림 연결이 잘못된 것이다.

### 2-2. 종류별 크기·무게 (바꾼 뒤 기준)

새 인형 k번째 그림은 type k 슬롯의 크기·무게를 받는다. 그래서 **원본 파일 번호 = type 번호**다(3-1절).

| type | 반지름 | 무게 | 느낌 |
| ---: | ---: | ---: | --- |
| 1 | 32 | 1 | 보통 |
| 2 | 30 | .9 | 조금 작고 가벼움 |
| 3 | 34 | 1.15 | 크고 무거움 |
| 4 | 29 | .85 | 작고 가벼움 |
| 5 | 33 | 1.05 | 조금 큼 |
| 6 | 31 | .95 | 보통 |
| 7 | 35 | 1.2 | **가장 크고 무거움** |
| 8 | 28 | .8 | **가장 작고 가벼움** |
| 9 | 33 | 1.1 | 크고 무거움 |
| 10 | 30 | .9 | 조금 작고 가벼움 |
| 11 | 32 | 1 | 보통 |
| 12 | 32 | 1 | 보통 (새 슬롯) |
| 13 | 30 | 1 | 조금 작음 (새 슬롯) |
| 14 | 34 | 1 | 큼 (새 슬롯) |
| 15 | 29 | 1 | 작음 (새 슬롯) |

- type 1~11은 **지금 값 그대로**다. 이미 쌓여 있는 기계가 예전과 똑같이 움직여야 하므로 절대 바꾸지 않는다.
- type 12~15는 1~4번의 반지름을 반복하고, 무게는 모두 1이다. 원본 엔진은 모르는 type의 무게를 1로 보기 때문에, 1이어야 원본 대조 테스트가 새 판에서도 맞는다.

### 2-3. 이미 쌓여 있는 기계

- 플레이어마다 기계가 하나씩 있고, 쌓인 인형 30개가 DB(`claw_accounts.board_json`)에 `{ id, type, x, y, radius, angle }`로 저장되어 있다. 지난 플레이 결과(`claw_plays.result_json`)에도 뽑은 인형의 `type`이 남아 있다. 미리보기 모드는 브라우저 저장소에 판을 둔다.
- **저장된 판은 그대로 둔다.** 거기에는 type 1~11만 있고, 그 그림 파일은 계속 있으므로(새 그림으로 바뀔 뿐) 따로 처리할 것이 없다. 지금 기계의 인형은 그 자리에서 새 1~11번 그림으로 보이고, 다 뽑으면 다음 기계부터 15종이 섞여 나온다.
- 서버가 판을 계산하고 브라우저가 같은 엔진으로 재생해서 결과를 맞춘다. 물리 값이 한쪽만 바뀌면 재생이 어긋난다. 상수는 `shared/`에 있어 양쪽이 같이 쓰므로, 3-3절 외에는 건드리지 않는다.

### 2-4. 원본 엔진 대조 테스트

`tests/claw-physics.test.ts`는 240가지 경우에 대해 **우리 `createBoard`·`simulateAttempt` 결과가 원본 JS(`tests/fixtures/gatcha-physics.original.js`)와 JSON까지 똑같은지** 검사한다. 원본에는 `DOLL_TYPES = 11`이 박혀 있어서, 15종으로 바꾸면 "생성된 판이 같다" 검사는 240개 모두 깨진다(미리 확인함). 고치는 방법은 3-4절에 정해 두었고, 그 방식이면 241개 검사가 모두 통과하는 것도 미리 확인했다. 그 방식대로만 고친다.

### 2-5. 서비스 워커

`scripts/build-sw.mjs`가 빌드 결과 전체를 해시해서 캐시 이름을 만들고, `/claw/dolls/*.webp`를 전부 미리 받아 둔다. 그림을 바꾸면 캐시 이름이 자동으로 바뀌어 새 그림이 내려간다. **캐시 처리 코드는 따로 필요 없다.**

## 3. 작업 순서

브랜치는 최신 `main`에서 새로 딴다. 한 PR로 낸다.

### 3-1. 원본 받기·번호 정하기

1. 사용자가 준 원본을 저장소 **밖** 임시 폴더(예: `/tmp/claw-dolls-src/`)에 둔다. 압축 파일이면 거기서 푼다.
2. 번호 규칙:
   - 파일 이름에 번호가 있으면(`1.png`, `doll-03.png`, `인형_7.jpg` 등) 그 번호를 type으로 쓴다.
   - 번호가 없으면 **파일 이름 오름차순**으로 1~15를 매기고, 보고서에 "type ↔ 원본 파일 이름" 표를 꼭 적는다. 사용자가 순서를 바꾸고 싶으면 다시 돌리면 된다.
   - 번호가 1~15에서 빠지거나 겹치거나, 15장이 아니면 멈추고 묻는다.

### 3-2. 그림 준비 스크립트: `scripts/prepare-claw-dolls.py` 고쳐 쓰기

기존 스크립트는 투명 PNG `gatcha-1~11.png`만 받는다. 이것을 **배경 있는 원본 15장**을 받도록 고친다. 같은 파일을 고치고, 새 스크립트를 따로 만들지 않는다.

사용법(목표):

```sh
python3 scripts/prepare-claw-dolls.py /tmp/claw-dolls-src [--output public/claw/dolls] [--preview /tmp/claw-dolls-preview]
```

장마다 이 순서로 처리한다.

1. **원본은 읽기만 한다.** 덮어쓰지 않는다.
2. **배경 지우기.** `scripts/cutout-characters.py`의 방식을 참고해서 만든다. 테두리 색의 중앙값을 배경색으로 보고, 테두리에서 시작해 배경색과 가까운 픽셀만 번지듯 채우는 flood fill이며, 밝기와 색차를 둘 다 쓰고 경계를 살짝 부드럽게 한다. 아래를 지킨다.
   - **바닥 그림자는 남기지 않는다.** (`cutout-characters.py`는 바닥 그림자를 살리지만, 인형뽑기 렌더러는 그림자를 직접 그린다. 그림자가 그림에 남으면 이중 그림자가 되고 인형이 떠 보인다.)
   - 인형과 이어지지 않은 작은 조각(섬)은 지운다. 알파 24 이하의 옅은 잡티는 0으로 만든다.
   - **인형 안쪽의 흰색·밝은 부분(눈, 배, 리본 등)은 지우지 않는다.** 테두리와 이어진 배경만 지운다. 팔과 몸 사이처럼 배경이 갇힌 구멍은 기본적으로 건드리지 않는다. 눈으로 봐서 배경이 분명히 남은 장만 그 장 전용 설정으로 처리하고 보고서에 적는다.
   - 장마다 허용 오차가 달라야 하면, 스크립트 안에 **type별 설정 표**(예: `OVERRIDES = {4: {"tol": 20}}`)를 두고 이유를 주석으로 적는다. 손으로 지우는 작업은 하지 않는다(다시 돌렸을 때 같은 결과가 나와야 한다).
   - 원본이 이미 진짜 투명(알파 있음)이면 배경 지우기를 건너뛴다.
   - 배경이 **체크무늬(가짜 투명 무늬)**거나, 그라데이션·무늬·사진이라 깔끔히 안 지워지면 그 장은 만들지 말고 멈춰서 어떤 파일인지 보고한다.
3. **투명 여백을 끝까지 자른다**(알파 > 0인 영역의 bbox로 crop). 결과의 알파 bbox는 이미지 전체여야 한다.
4. **긴 변 320px**로 Lanczos 축소, 종횡비 유지. 원본이 320px보다 작으면 키우지 말고 멈춰서 보고한다.
5. WebP 저장 설정은 기존과 같다: RGB `quality=85`, `alpha_quality=100`, `method=6`, `exact=True`. 저장 후 다시 읽어 크기와 알파 채널이 그대로인지 검사한다(기존 스크립트의 검사 유지).
6. 장당 **40,000바이트 이하**. 넘으면 실패시키고 보고한다. 품질을 몰래 낮추지 않는다.
7. 출력은 `public/claw/dolls/doll-1.webp` ~ `doll-15.webp`. 기존 1~11번은 덮어쓴다. 폴더에 이 15개 외의 파일이 남지 않게 한다.
8. `--preview` 폴더(저장소 밖)에 **확인용 모아보기 이미지**를 만든다. 15장을 ① 기계 배경색 `#E3F1FC`, ② 어두운 색 `#3A3340`, ③ 체크무늬 위에 각각 나란히 놓은 그림 3장이다. 배경 찌꺼기·흰 테두리·구멍을 눈으로 확인하는 용도이며 커밋하지 않는다.
9. 기존처럼 표준출력에 Pillow·libwebp 버전, type별 원본 파일 이름·원본 바이트·WebP 바이트·크기, 합계를 찍는다.

스크립트 맨 위 docstring도 새 사용법에 맞게 고친다.

### 3-3. 코드 수정 (이 범위만)

**(a) `shared/claw-physics.ts`**: 이 세 줄과 위의 주석만 바꾼다.

```ts
export const DOLL_TYPES = 15;
// Relative weight of each sprite type (1..15). Heavier dolls slip out of a weak claw sooner.
// Types 12..15 weigh 1: the original engine treats any type it does not know as 1.
export const DOLL_WEIGHT = Object.freeze([1, 1, .9, 1.15, .85, 1.05, .95, 1.2, .8, 1.1, .9, 1, 1, 1, 1, 1]);
// New machines get slightly different sizes per type, so the pile packs unevenly like plush toys.
export const DOLL_RADIUS = Object.freeze([32, 32, 30, 34, 29, 33, 31, 35, 28, 33, 30, 32, 32, 30, 34, 29]);
```

앞의 12칸(0번 칸은 미사용 + type 1~11)은 지금 값과 한 글자도 다르지 않아야 한다.

**(b) `scripts/build-sw.mjs`**: 주석 `all 11 /claw/dolls/*.webp`의 숫자만 15로 고친다. 동작은 바꾸지 않는다.

그 밖의 소스 코드는 고치지 않는다.

### 3-4. 테스트 수정

**(a) `tests/claw-physics.test.ts`**: 원본 대조를 유지하는 방식으로 고친다. fixture 파일은 건드리지 않는다.

- blob SHA 테스트는 그대로 둔다.
- 240개 경우마다 아래를 검사한다. `input`을 만드는 방식(벽·인형 중심·임의 위치, 정지 위치, 집게 힘)은 지금 코드 그대로 쓰되, 판마다 그 판의 인형으로 `target`을 고른다.
  1. **저장된 옛 판:** `const oldBoard = original.createBoard(g, s)`에 대해 `simulateAttempt(oldBoard, …, {record:true})`와 `original.simulateAttempt(oldBoard, …, {record:true})`의 JSON이 같다. 이미 쌓여 있는 기계가 예전과 똑같이 움직인다는 보장이다.
  2. **새 판:** `const board = createBoard(g, s)`에 대해 `simulateAttempt(board, …)`와 `original.simulateAttempt(board, …)`의 JSON이 같다.
  3. 기존의 프레임 수 범위 검사(`> 0`, `<= 1024`)는 두 경우 모두 유지한다.
- `createBoard` 검사를 추가한다: 인형 30개, id 중복 없음, 모든 type이 1~15 정수, 각 인형의 `radius === DOLL_RADIUS[type]`, 같은 (세대, 시드)면 같은 판, 240개 경우를 합치면 1~15가 모두 한 번 이상 나온다.
- `DOLL_WEIGHT`·`DOLL_RADIUS`의 앞 12칸이 원본 fixture의 같은 배열과 같다는 검사를 추가한다(fixture가 export한다).
- `JSON.stringify(createBoard(g, s)) === JSON.stringify(original.createBoard(g, s))` 검사는 종류 수가 달라 성립할 수 없으므로 이것만 빼고, 빼는 이유를 주석 한 줄로 남긴다.

**(b) `tests/integration.test.ts`**: `doll.type <= 11`을 `doll.type <= DOLL_TYPES`로 바꾸고 `DOLL_TYPES`를 import한다.

**(c) `tests/e2e/claw.spec.ts`**: 미리 받아 둔 인형 그림 수 `toBe(11)`을 `toBe(15)`로.

### 3-5. 문서

- `docs/asset-provenance.md` 맨 위 **「캐릭터 뽑기 인형 이미지 출처」** 절을 새 그림 기준으로 다시 쓴다. 다른 절은 건드리지 않는다. 담을 것:

  - 제작 환경(Python, Pillow, libwebp 버전).
  - type ↔ 원본 파일 이름 ↔ 원본 크기·바이트 ↔ WebP 바이트·크기 표와 합계.

### 3-6. 공지 (`shared/notices.ts`)

이 저장소 규칙(`CLAUDE.md`)상 플레이어가 느끼는 변화이므로 공지를 쓴다.

- `NOTICES` 배열 **맨 위**에 추가한다. `date`는 작업일 KST `YYYY-MM-DD`, `id`는 `YYYY-MM-DD-new-claw-dolls`.
- **같은 날짜의 공지가 이미 맨 위에 있으면** 새 글을 만들지 말고 그 글의 `items`에 항목을 더한다(`id`는 그대로).
- 플레이어가 읽는 글이다. 파일·코드·DB 같은 기술 내용은 쓰지 않는다. 사용자가 문구를 따로 주면 그것을 쓰고, 아니면 아래를 쓴다.

  ```ts
  {
    id: 'YYYY-MM-DD-new-claw-dolls',
    date: 'YYYY-MM-DD',
    title: '캐릭터 뽑기에 새 인형들이 들어왔어요',
    summary: '뽑기 기계 속 인형이 새 얼굴 15종으로 바뀌었어요.',
    items: [
      { title: '새 인형 15종',

      { title: '지금 기계도 그대로',
        body: '이미 쌓여 있던 인형은 그 자리 그대로 새 그림으로 보여요. 다 뽑으면 다음 기계부터 15종이 골고루 섞여 나와요.' },
    ],
  },
  ```
